   可用率不是 100%**；
3. **人工抽 5 篇看不出的规律，自动化一次就抓到了**：那 2 篇 `/G` 乱码里，
   1 篇不在我的手工抽查名单里——是 `index scan` 的可疑检测抓出来的。

## 2. 关键设计

### 2.1 两套语料并存：谁复现什么

换语料最危险的动作是"覆盖"——一旦 `data/corpus/` 被真资料顶掉，第 16~19 周的数字就再也跑不出来了。
所以这次是**搬迁而不是替换**：

| 目录                | 内容                       | 用它的地方                                   |
| ------------------- | -------------------------- | -------------------------------------------- |
| `data/corpus-notes/`| 第 1~18 周笔记快照（23 篇） | 复现 G2：`--index data/index-notes`（465 片段） |
| `data/corpus/`      | **44 篇真实论文**           | 默认索引 `data/index`（2501 片段），G3 起用它  |

默认值指向新语料（日常使用顺手），**旧数字要跑就显式写 `--index data/index-notes`**——
这条已写进 `学习进度.md` 的运行手册，避免"跑出来对不上"时误以为代码坏了。
两个目录都在 `data/` 下，都不进 Git。

### 2.2 换语料的固定动作：先预检、再建库

预检（`scan`）只解析不编码，**22s**；全量建库 **103.6s**（fastembed，含向量化）。
差 5 倍的代价差，换来的是先看清三张清单：

```text
index scan →
  ① 解析失败（文件读不开 / 格式不支持）
  ② 空文档（一个字都没提取到 —— 扫描版 PDF 的典型症状）
  ③ 文字层可疑（正文里成片出现 /G 字形编号 —— 缺 ToUnicode 映射）
```

**为什么值得单独做一个命令**：第 16 周那套解析层只保证"不崩"，
`build` 里"失败只记录不中断"也是同一思路——但**记录不等于被看见**。
44 篇里真出问题的那 2 篇，`build` 只会告诉你"0 失败"（它们确实解析成功了），
只有 `scan` 会指出"抽出来的正文不可读"。这条对应台账里反复出现的教训：
**跳过 / 降级必须有自己的观测输出**（T2 / T22 同源）。

### 2.3 两条大小上限，两个值域（T31）

| 常量               | 值      | 用在哪                 | 为什么是这个量级                                     |
| ------------------ | ------- | ---------------------- | ---------------------------------------------------- |
| `MAX_FILE_BYTES`   | 1 MiB   | `search_notes`（笔记工具） | 一份笔记 1 MiB 已经异常大，超了跳过并回传 `skipped_large_files` |
| `MAX_PARSE_BYTES`  | 64 MiB  | `parsers.py`（语料解析） | 论文 PDF 5~20 MB 很常见，图像多的能到 25 MB；64 只挡"明显不是文档"的文件 |

修法上的关键选择：**没有把 1 MiB 改成 64 MiB 了事**。
`MAX_FILE_BYTES` 是**产品行为**（工具该拒绝多大的输入），`MAX_PARSE_BYTES` 是**工程保护**
（别把 1 GB 的垃圾读进内存）。共用一条常量的后果是"改动一个，另一个的语义跟着漂移"——
所以拆开后，笔记工具那 4 条既有的大小限制测试**一行没改就通过了**，
这本身就是"没有顺手放宽工具侧边界"的证据。

### 2.4 语料遍历：隐藏目录也要跳过

`_iter_corpus_files` 原来只按后缀过滤，`corpus/.trash/x.pdf` 这种会被收进索引。
真实资料是"人手工整理"的目录，隐藏目录（`.trash/` / `.DS_Store` 之类）一定会出现，
所以补了"隐藏目录整棵子树跳过"。**这条护栏的边界要说清**：它只挡 `.` 开头的目录，
**正常命名的子目录仍会被遍历**——要排除某篇论文就得挪到 `corpus/` 之外的 `data/corpus-excluded/`
（见 `rag/解析质量抽查.md` 第〇节）。

### 3.2 精读 5 篇的结论

| 维度                | 结论                                                                 |
| ------------------- | -------------------------------------------------------------------- |
| 页码 / 标题路径      | **可靠**（抽查里 1~14、1~22 页都对）——这是"引用可回查"的基础，符合预期 |
| 正文段落            | 中文、英文（Coatings 2024）都能完整抽出                              |
| 表格 / 公式          | **普遍丢失或拍平**（pypdf 固有限制）：引用数值会指向"一串数字"        |
| 文字层质量          | 1 篇 OCR 产物（`博士`→`博十`、`Vol-30 NO．1`）；2 篇缺 ToUnicode（`/G` 乱码） |

按子主题挑的 5 篇里，2 篇/篇的判定是"中"或"差"——**这不是解析器的锅，是源文件的质量**。
所以处置也分开：解析器能改的（页码、切分）继续改；
属于源文件的（缺 ToUnicode、OCR 错字）只能换版本或标注，记进清单让下游知道。

### 3.3 自动可疑检测：为什么值得单独做

`scan` 的"文字层可疑"判据：**片段里成片出现 `/G<数字>` 形式的 token**。
命中 2 篇，都出自《计算机集成制造系统》（2010、2019）：

| 文件（子主题）                                        | 片段 | 后果                                   |
| ----------------------------------------------------- | ---- | -------------------------------------- |
| `数字孪生与智能车间/数字孪生五维模型及十大领域应用…2019.pdf` | 18 | 正文不可读，**不在我手工抽查的 5 篇里** |
| `数控编程与轨迹规划/参数曲线的自适应实时前瞻插补算法…2010.pdf` | 5  | 正文不可读（这篇在我精读名单里）        |

**处置（使用者 2026-10-08 决定）**：不换版本，按"**仅存在性可检索**"使用——
标题/期刊/年份可读，可以当"这个方向有这篇文献"的证据；
但**不能当正文来源引用**，第 21 周引用回查要避开它们。

同一本期刊命中两篇，更像是该刊某些年份的 PDF 没带 ToUnicode 映射；
**同一期刊的其它论文也要留意**（这句已写进抽查记录，换语料时复看）。

## 4. 踩坑

1. **T31：一条常量被两件事复用**（本周唯一的功能性 bug）。
   现象是"29/44 篇论文没进索引，但测试全绿、日志只报 0 失败"。
   根因是解析层复用了笔记工具的 1 MiB 上限。**这类 bug 的特征是"错在一个不在你视野里的地方"**：
   改 `parsers.py` 时看的是解析逻辑，不会去看 `tools.py` 里的常量语义。
   教训：**常量的"值"和"语义"要一起定义**——`MAX_FILE_BYTES = 1 MiB` 这个名字本身就
   容易让人以为它是"所有文件的上限"。
2. **`index scan` 的价值是"便宜地看清单"**：22s vs 103.6s，5 倍差价。
   如果先建库再看结果，我会多花一次全量时间才发现问题（第 14 周"先测便宜的那个"的同一课）。
3. **`--verify` 是对 T29 的定向防御**：索引向量错位是"静默"的（检索还能跑，只是永远差一点）。
   抽查 8 条重算余弦，成本几乎为零，但能把这类错误变成"不通过"。
   注意它**只是抽查**——`sample=8` 命中不了"只有某几行错"的情况，真要严谨得全量校验（暂不做）。
4. **报告要脚本生成**：`eval/建库报告.md` 文件头写着"语料变了请重跑，不要手改数字"。
   手改的报告会变成第二份真相来源，和 T29 那类"数据没变、标签变了"是同一个坑。
