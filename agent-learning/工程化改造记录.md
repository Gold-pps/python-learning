### T1 `search_notes` 不再全量读入大文件

| 项       | 内容                                                                                                                                                                                                                                                                                                                          |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 现象     | `read_note` 有 1MB 上限，`search_notes` 没有任何大小限制：搜索会对每个 `.md` 直接 `read_text()` 全量读入。                                                                                                                                                                                                                    |
| 根因     | 大小检查缺位，且**检查的位置**比"有没有检查"更关键——必须放在 `read_text()` 之前，否则"检查"本身就已经把文件读进内存了。这是一个典型的"看起来是缺功能、其实是缺顺序"的问题。                                                                                                                                                   |
| 改法     | `tools.py / search_notes`：取 `st_size` 超过 `MAX_FILE_BYTES` 就跳过并计数；两个工具对同一个限制采取了不同策略——`read_note` **报错**（用户要的就是那一个文件，静默返回空内容更糟），`search_notes` **跳过并计数**（一个坏文件不该让整次搜索失败）。计数回传字段 `skipped_large_files`，防止模型把"没搜到"误当成"笔记里没有"。 |
| 验证     | 造一个 1MB+ 的探针文件，里面埋独有关键词 `UNIQUE-BIG-KEYWORD`：修复后返回 `{'ok': True, 'matches': [], 'skipped_large_files': 1}`（关键词搜不到，但明确告知跳过了 1 个文件）；同期正常搜索 `护栏` 返回 5 条、`skipped_large_files: 0`，未受影响。`eval_cases.py --unit-only` 仍 12/12。                                       |
| 影响面   | 工具返回值新增字段，`notes-qa/项目设计.md` 的工具输出说明待同步（排入第 15 周"文档收口"）。                                                                                                                                                                                                                                   |
| 决策记录 | 本条的**固定单元用例**留到第 14 周：那一周要把手写 `UNIT_CASES` 整体迁到 pytest，用例数量会变，此刻插一条会让"12 条"这个口径在第 13、14 周之间来回改。临时验证已用一次性脚本做掉。                                                                                                                                            |

### T2 评估探针不再残留（`os.rmdir` → `os.unlink`）

| 项     | 内容                                                                                                                                                                                                                                                                                                                                                |
| ------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 现象   | 每次跑 `eval_cases.py --unit-only`，仓库里多出一个**断链** `agent-learning/_probe_linkdir.md`（指向已删除的 `_probe_linkdir_target`）。测试**全部通过**，却污染了工作区——这类"绿灯下的脏数据"最容易长期存活。                                                                                                                                       |
| 根因   | U6 的 `finally` 里用 `os.rmdir(link)` 删除**符号链接**：`os.rmdir` 只能删目录本身，符号链接对它来说不是目录，于是抛 `NotADirectoryError`；而 `except OSError: pass` 把这声报错吞掉了，最终表现为"测试全绿 + 仓库多一个断链"。原注释只考虑了"junction 要 rmdir"，漏了"符号链接必须 unlink"——**分支写少了，而且少的那一支恰好是当前平台走的那一支**。 |
| 改法   | 拆成两个分支：`is_symlink()` → `os.unlink()`；`is_junction()` → `os.rmdir()`。顺序不能反：Windows 上 junction 的 `is_symlink()` 为 False，Linux 上 `is_junction()` 恒为 False，两者互不干扰。                                                                                                                                                       |
| 验证   | ① 最小复现已证明 `os.rmdir` 抛 `NotADirectoryError`、`os.unlink` 成功；② 修复后重跑 `--unit-only` 得到 12/12，且 `ls agent-learning/_probe_*` 与仓库根均无残留。                                                                                                                                                                                    |
| 影响面 | 遗留风险：`finally` 里仍然 `except OSError: pass`，清理失败依然**只留痕迹、不报警**。根治办法是第 14 周迁到 pytest 时把探针挪进 `tmp_path`——临时目录本身由 pytest 兜底回收，不再依赖手写清理逻辑的正确性。                                                                                                                                          |

最小复现（不依赖任何项目代码，可换机重放）：

import os, pathlib
link = pathlib.Path("link")                    # 指向某个目录的符号链接
print(link.is_symlink(), link.is_junction())   # True False

### T3 `main.py` 的会话历史收敛到常数规模

| 项     | 内容                                                                                                                                                                                                                                                                                                            |
| ------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 现象   | 交互式问答里 `ask()` 直接 `return result.to_input_list()`，history 只增不减：每一轮的输入 = 全部历史 + 本轮问题。会话越长，每问一句要重发的输入越多，同时 history 列表本身占的内存也在涨。                                                                                                                      |
| 根因   | `to_input_list()` 会把本轮**工具返回的原文**一起写进历史——`read_note` 一次最多 200 行，一轮能塞进几千字符，于是输入规模随轮数**线性增长**。缺少的不是某个功能，而是"历史这个数据结构的容量策略"：它被当成只写不读的内存用，没人负责收敛。                                                                       |
| 改法   | `main.py` 新增 `MAX_HISTORY_TURNS = 8` / `MAX_HISTORY_ITEM_CHARS = 2000` 两个常量，以及 `_truncate_text` / `_trim_item` / `_keep_recent_turns` / `prepare_history` 四个函数；收敛动作只放在 `ask()` 的**写入侧**一处：`return result.final_output, prepare_history(result.to_input_list())`。三个关键设计见下。 |
| 验证   | 见下方"实测数据"。另：`--unit-only` 仍 12/12，无 `_probe_*` 残留。                                                                                                                                                                                                                                              |
| 影响面 | `MAX_HISTORY_TURNS = 8` 是**初值**，等第 22 周拿到真实使用日志后再按"够不够用 / 贵不贵"调；本轮只做了字符数代理指标，真实 token 曲线用 `notes-qa/exp_history_tokens.py --no-trim` 对照跑（见下）。                                                                                                              |

**实测脚本**：`notes-qa/exp_history_tokens.py`（2026-09-18 新增）。两臂只差一处——
`--no-trim` 时把 `result.to_input_list()` 原样存下（等价于修复前那一行），其余路径完全相同，
所以曲线可比。脚本会打印每轮 `输入 / 缓存命中 / 输出 / history 体积 / 耗时`，并算出高峰价与低谷价的
成本估算，最后输出可直接贴进笔记的表格行。

跑之前先定判据（**先定判据再跑，避免看到数字再找解释**）：

1. 修复后：第 9 轮起输入 token 应基本持平（上限 8 轮）；若仍持续增长，说明有内容没被截断；
2. 修复前：输入 token 应接近线性增长，末轮约为首轮的数倍；
3. 两臂的第 1 轮**不会完全相同**——冒烟测试的实测值是 `18,321`（收敛臂）对 `14,834`（不收敛臂），差 23%。
   即使 `temperature=0`，模型这一轮调几次工具、每次读多少行仍会变，所以第 1 轮只能"量级相近"。
   **判据要看趋势（线性 vs 持平），不要逐点比对**；想更稳就把同一臂跑 2~3 次看趋势是否一致；
4. 额外看**缓存命中**那一列：截断让窗口滑动，前缀不再稳定，命中率可能下降。
   若"省下的 token"被"降低的缓存命中率"部分抵消，这条曲线的结论就要写成
   "token 线性增长被止住，但单位成本未必同比例下降"——这正是第 7 周笔记里缓存价那条经验的延伸。

**冒烟测试记录（2026-09-18，各 1 轮，用于验证脚本本身）**：

| 臂     | 输入   | 缓存命中 | 输出  | history             | 耗时  | 低谷价    |
| ------ | ------ | -------- | ----- | ------------------- | ----- | --------- |
| 收敛   | 18,321 | 14,080   | 2,465 | 25 条 / 13,816 字符 | 13.7s | ≈0.015 元 |
| 不收敛 | 14,834 | 11,136   | 1,959 | 21 条 / 14,641 字符 | 12.0s | ≈0.013 元 |

两条附带结论：① 单轮输入就有 1.5~1.8 万 token——工具调用循环（search → read → 回答要 3~4 次请求，
每次重发全文）才是本项目最大的输入来源，历史累积是叠加在这之上的；② 单轮成本约 1.5 分钱，
8 轮 × 两臂合计预计 **0.3~0.6 元**（低谷价），比最初"不到一毛"的估计高一档，按实际数字记账。

**真实 token 曲线结论（2026-09-18，两臂各 8 轮，数据见 `第13周笔记.md` 第 3.4 节）——本条验证要改写**：

|                                           | 收敛臂                    | 不收敛臂                  |
| ----------------------------------------- | ------------------------- | ------------------------- |
| 输入 token 合计 / API 请求数 / 缓存命中率 | 389,573 / 25 次 / **82%** | 503,415 / 29 次 / **95%** |
| 低谷价                                    | 0.151 元                  | 0.080 元                  |

1. **修复在 8 轮规模下几乎没生效**：`MAX_HISTORY_TURNS=8` 正好被 8 轮用满、从未触发；
   单条 2000 字符上限也没触发（两臂 history 体积 79,712 vs 83,695 字符，条目平均约 800 字符）。
   → 原先"字符数验证通过"只证明了逻辑正确，**没有证明收益存在**。
2. **主导变量是"该轮工具往返次数"，不是历史长度**：请求次数实测在 1~7 次波动，
   单轮输入 = 请求次数 × 每次重发的上下文，第 4 轮 7 次请求直接顶到 118,640 token。
3. **噪声大于效应**：第 1 轮两臂代码路径完全相同，却跑出 7,659 vs 15,297（2 倍）→ n=1 不能比较两臂。
4. **新假设（待验证）**：截断改变历史内容 → 下一轮前缀与已缓存前缀不一致 → 缓存命中率下降（82% vs 95%）。
   缓存命中价只有未命中的约 1/50，**破坏缓存可能比省下的 token 更贵**。
5. **参数要按真实规模重定**：真实使用是"一次提问 1~7 次工具往返、单条返回约 800 字符"，
   所以 `8 轮 / 2000 字符` 属于拍脑袋初值；要么调到会被触发的量级，要么用 15~20 轮重测。

**这条经验的普适版本**：一个修复"逻辑正确"和"有收益"是两件事，**验证必须用真实规模的负载**。
合成负载（6 KB/条、20 轮）证明了正确性，真实负载（800 字符/条、8 轮）证明了它没用武之地——
两个结论都对，只有后者能决定要不要保留这个复杂度。

三个关键设计（这部分比代码本身值钱）：

1. **必须从 `user` 消息处切开**。一条 user 消息 + 它引发的 `function_call` / `function_call_output` / 最终回答才是完整一轮。从中间切会留下"没有对应 `function_call` 的 `function_call_output`"（孤儿工具结果），发给 API 会被直接拒掉——这个坑只在被截断的那一次才暴露，很容易漏到线上。
2. **收敛只做在写入侧一处**。history 是"只在这里写、只被下一轮读"的数据，在写入口收敛一次，就不需要在每个用到 history 的地方各截一遍；两处各截一次的逻辑迟早会分叉。
3. **截断返回副本**（`_trim_item` 里 `dict(item)` + 重建 list），不改调用方给的原对象。改历史副本和改工具返回值是两回事：工具返回值是"这一轮模型要看的资料"（不能动），历史副本只是"下一轮还需要记住的摘要"。

未触上限的短会话逐条等价（`prepare_history(small) == small` 为 True），说明截断逻辑不会"顺手改动"正常历史。

最小复现方法（无需联网，任何人可重放）：

```python
import json, main

def make_turn(i, tool_chars=6000):
    return [
        {"role": "user", "content": f"第 {i} 问"},
        {"type": "function_call", "name": "read_note", "call_id": f"c{i}", "arguments": "{}"},
        {"type": "function_call_output", "call_id": f"c{i}",
         "output": json.dumps({"ok": True, "content": "正" * tool_chars}, ensure_ascii=False)},
        {"role": "assistant", "content": f"第 {i} 答"},
    ]

history = [it for i in range(20) for it in make_turn(i)]
print(len(history), "->", len(main.prepare_history(history)))
```

**决策记录**

- 常量放 `main.py` 而非 `config.py`：`config.py` 管"怎么连模型"（地址、超时、重试），这两条管"这个命令行会话怎么记事儿"，与 `MAX_QUESTION_LEN` 同类。
- 没有做"早期对话摘要"（用模型压缩老历史）：那是每轮都要多花一次模型调用和一次失败可能性的设计，等 T3 的简单上限被真实使用打脸（比如第 22 周发现"忘了第 2 轮说过什么"）再加，先上便宜的。
- 截断用字符数而不是 token 数：`tiktoken` 是 OpenAI 的分词器，对 DeepSeek 不精确，为估算再引一个依赖不划算。字符数是保守代理，量级判断够用。
- 截断痕迹写进内容本身（`…[历史截断，原文 N 字符]`）：模型能看见"这里被省略了"，比静默丢字更不容易产生"我被喂了完整资料"的错觉。

### T4b `~/.codex/config.toml` 的明文 API Key 改环境变量注入

| 项     | 内容                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 现象   | Codex 的全局配置里，自定义 provider 的凭据是明文：`experimental_bearer_token = "sk-…"`。这个文件是会被分享、截图、贴进 issue 的典型对象。                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| 根因   | 配置里同时用了"把密钥写死在配置中"的字段（`experimental_bearer_token`）。Codex 的 `ModelProviderInfo` 还有另一个字段 `env_key`，语义是"凭据从环境变量取"，正是为这种情况准备的（字段来源：本机 codex 二进制内的配置结构，并用 `codex exec --strict-config` 验证过它被识别——严格模式只对 `preferred_auth_method` 报未知字段，没报 `env_key`）。                                                                                                                                                                                                                                            |
| 改法   | ① 备份原配置到 `/tmp/python-learning-trash-20260918/config.toml.bak`（600）；② `sed` 删掉 bearer 行、在 `wire_api` 后加 `env_key = "DEEPSEEK_API_KEY"`（用 `sed` 而不是编辑器补丁，是为了让密钥值不出现在任何命令、日志或对话里）；③ 密钥本体写进 `~/.config/deepseek/api.env`（600），由 `~/.bashrc`、`~/.profile` 各引一次；④ 因为 VS Code 是 **systemd 直接拉起**的（`ps` 显示父进程是 systemd，`/proc/<pid>/environ` 里没有该变量），shell rc 覆盖不到 GUI 启动路径，所以再加 `~/.config/environment.d/deepseek.conf`（600），并用 `systemctl --user import-environment` 做即时注入。 |
| 验证   | 见下方"实测矩阵"。真实调用共两次（隔离环境一次 + 真实配置一次），各约 1.5k tokens。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |

## 跨阶段的方法论备注

1. **改前先能复现**：T2 的价值一半来自那条最小复现命令——它把"某天测试跑完多了个文件"变成了 5 行、可在任何机器上重放的事实。
2. **注意"绿灯下的脏数据"**：测试通过 ≠ 系统干净。清理逻辑要有独立的验证手段（本例是 `ls`/`git status`），不能靠测试结论倒推。
3. **同一个常量、两种策略**：`MAX_FILE_BYTES` 在 `read_note` 是"报错"，在 `search_notes` 是"跳过 + 计数"。别为了"统一"把两种合理语义强行合并。
4. **别猜第三方库的数据结构**：T3 的截断逻辑整个建立在"`to_input_list()` 返回 dict、工具返回塞在 `output` 字符串里"这个前提上。这个前提是打开 `.venv/.../agents/items.py` 读出来的，不是猜的——猜错的后果很隐蔽：代码照常运行，一个字符也没截到，而且没有任何报错。**函数签名同样算"数据结构"**：写实测脚本时我猜 `Runner.run(..., model_settings=...)`，实际是 `run_config=RunConfig(model_settings=...)`。数据猜错是静默失效，参数名猜错是当场 `TypeError`——后者其实更幸运。查签名的成本是 10 秒，返工的成本是一轮往返加一次被用户撞见的报错。
5. **"清理文件"和"密钥泄露"是两种性质，用 git 历史来区分**：删任何带密钥的文件之前，先 `git log --all --name-only` 查它进没进过提交。没进过 = 本地卫生问题，删掉即可；进过且 push 过 = 已经泄露，必须轮换密钥，此时"删掉文件"只是自欺欺人。T4a 的结论是前者，所以可以放心删。
6. **改配置先备份，并先想好回滚命令**：T4b 是本周唯一会让人"打不开工具"的改动。备份特意放在 `/tmp`（重启即清空的临时位置），避免为了回滚反而多留一份长期密钥副本；台账里直接写可执行的回滚命令，而不是"如有问题请恢复备份"。
7. **同一个秘密别到处抄**：为了覆盖终端、GUI、脚本三种启动路径，很容易在 `.bashrc`、`.profile`、`environment.d` 里各抄一份密钥。原则是**密钥本体只存一份（600 权限），其他位置只放"引入"这一行**。唯一的例外是 `environment.d`——它不是 shell，没有 source 机制，只能内联值；遇到这种必须重复的情况，要在台账里写清"哪一份是真副本、为什么必须重复"，否则半年后没人分得清哪个能删。
8. **贴输出之前先问一句"它会落到哪"**：验证类命令的输出常常自带敏感值（`env`、`systemctl --user show-environment`、`printenv`、带凭据的 URL）。终端里看一眼没问题，**但一旦贴进对话，它就同时进了会话记录、本地 rollout/sqlite，并会随上下文发给模型服务**。自检习惯：先把输出过一遍 `grep -v` 或做成"只看键名/只看长度"，再决定贴什么。这一条要是当初就执行了，T5 整节都不必存在。
9. **别用 git 的还原命令清"自己的临时改动"**：`git checkout -- <path>` / `git restore` 是**文件级**的，会把该文件所有未提交改动一起抹掉，而且**不会报错**（T9 的现场：文件从"已修改"变成干净，看起来像是"清理好了"）。清临时行用 `apply_patch`；要造污染做验证，就写临时文件或 `tmp_path`，别碰真实文档。

10. **同名的常量会随“被谁用”漂移语义**：`MAX_FILE_BYTES` 原本只回答“笔记工具该接受多大输入”，被解析层复用后，它悄悄兼任了“所有文件的上限”——改值前先问“**这个边界属于谁**”。T31 的现场是：工具侧测试全绿、日志报 0 失败，而 29/44 篇论文没进索引。同名不等于同义，见第 3 条（同一个常量两种策略是有意的；这次是无意的复用）。

11. **预算要按“产物要写多长 + 模型要想多久”给，而且别贴脸**：我们要求的结构（四段式 JSON ≈1.2k token）加上推理型模型自己的思考（2.5k~4k token），决定了 `max_tokens` 该给 8192 而不是 4096；盘点那一步实测 2043 而预算恰好 2048 —— **贴脸等于没给**（差 5 个 token 就白跑一次）。上限只在真生成时付费，留余量比省额度划算得多。见 T32。

### T17 `Chunk.id` 在长文本按句切时冲突

| 项     | 内容                                                                                                                                                                                                                                         |
| ------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 现象   | `test_chunk_blocks_multiple_chunks_have_unique_ids` 报 `assert 4 == 3`：同一段文本切出的 4 个 chunk 只有 3 个不同 id。id 列表里 `t.md:2:5e6a1222f370c94f` 出现了两次。                                                                       |
| 根因   | `Chunk.id` 的构成是 `source_path:start:hash`。长文本按句切时，**同一行会产出多个 chunk，它们的 `start` 相同**；如果切出的文本内容恰好相同（如"这是一句话。"重复 300 次），`hash` 也相同 → id 相同。id 是索引主键，重复会让两个片段互相覆盖。 |
| 改法   | `chunk_blocks` 末尾加去重：遍历时用 `seen` 记每个 id 出现次数，第二次起用 `replace(c, id=f"{c.id}-{n}")` 加后缀。                                                                                                                            |
| 验证   | `uv run pytest -q` → **56 passed**（含那条之前失败的用例）；`uv run ruff check .` → All checks passed。                                                                                                                                      |
| 影响面 | **这是本周唯一"如果不写测试就会漏到线上"的问题**：`Chunk.id` 重复后，`chunks.jsonl` 里两个片段 id 相同，第 17 周做索引时后写的会覆盖先写的，检索结果静默变少——而且不报错。                                                                   |

### T19 双后端实测："有 GPU 就用 GPU"被推翻

| 项                                                       | 内容                                                                                                                                                                                                                   |
| -------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 背景                                                     | 第 17 周实现了两个向量化后端：`bge`（sentence-transformers + torch + CUDA）与 `fastembed`（ONNX + CPU）。原计划 fastembed 只作为 Linux 那台 7.2 GB 机器的降级方案。用户要求保留 Linux 可跑性，因此两分支都实现并实测。 |
| 实测（Windows + RTX 3050 Laptop + 15.7 GB，60 条短文本） | `bge` 冷启动 13.08s / 热启动 0.021s；`fastembed` 冷启动 **0.33s** / 热启动 0.035s。**小批量下 fastembed 反而快 40 倍。**                                                                                               |
| 实测（22 篇真实语料 / 431 片段）                         | `bge` 冷启动 15.58s、内存增量 ~1116 MB；`fastembed` 冷启动 14.82s、内存增量 ~941 MB。两后端都 <1.5 GB（规划验收线）。交叉相似度 **1.0**（同模型不同实现，向量实质等价）。                                              |
| 结论                                                     | **torch 加载 CUDA 上下文要十几秒，ONNX 加载只要零点几秒。** GPU 推理吞吐的优势要批量足够大才盖过加载成本。**对本项目典型规模（几十到几百 chunk），fastembed 更快。**                                                   |
| 影响面                                                   | ① 后端选择不再按"有没有 GPU"，而按**批量大小 + 是否反复调用**；② fastembed 的定位从"降级方案"升级为"常规选项"；③ 结论写进 `embedder.py` 的 docstring，下次改之前先看那一段。                                           |

**这条推翻的是一条常识**："有更快的硬件就一定要用它"。真正该算的是**总耗时 = 加载 + 推理**，
加载成本在短任务里是主导项。同理，将来评估 LLM 重排时，也要先看"每次要付多少固定开销"。

### T24 `RERANK_GAP` 实测：这个触发条件在 RRF 上形同虚设

| 项     | 内容                                                                                                                                                                                                                                                                                                                                                                                                     |
| ------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 现象   | 规划规定"相邻候选的 RRF 分数差 < `RERANK_GAP`（初值 0.01）才触发重排"。离线在 10 题上实测：**8/8 全部触发**；阈值一路降到 0.0005 仍是 8/8。                                                                                                                                                                                                                                                                |
| 根因   | RRF 的分是一组离散值，两路互相补偿时不同片段会**恰好相等**（`1/62 + 1/63 == 1/63 + 1/62`），于是"候选池内相邻最小分差"恒为 0，任何 gap 都满足"< gap"。这不是实现 bug，是**指标选错了**：第 15、16 名黏在一起，对"取前 5 条"没有任何影响。                                                                                                                                                                    |
| 改法   | 本周**只测不改**（阈值该定多少需要真实重排数据，第 19 周和"重排值不值这个钱"一起定）。对比脚本改为同时输出两个视角：A 候选池内任意相邻；B **切分点**（第 k 名与第 k+1 名）。                                                                                                                                                                                                                                |
| 验证   | B 视角下各题分差 0.00026 ~ 0.00996；`gap=0.001 → 5/8`、`gap=0.0005 → 4/8`，与"边界真的模糊"的直觉一致（A 视角则永远是 8/8）。                                                                                                                                                                                                                                                                              |
| 影响面 | 规划风险表里"重排导致成本上升 → 关掉重排"这条暂时用不上：**本周的结论是触发条件形同虚设，而不是成本太高**。第 19 周要把"阈值怎么定"和"重排到底值不值"一起回答；若最终改成切分点视角，`should_rerank()` 的语义要改，测试也要跟着改。                                                                                                                                                                          |

### T35 引用回查全过，但答案仍可能被误用：语境与术语的保真

| 项     | 内容                                                                                                                                                                                                                                                                                                                                            |
| ------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 现象   | 三次真实使用共 50 条引用，代码校验**全部精确可回查、0 编造**；把 5 条数值/表述拉回原文逐字比对也全对。但人工读的时候发现风险不在“抄错”，而在**拿错语境**：① 答案引用的 `S=60 r/min、af=0.05 mm/r、ap=0.02 mm` 出自**超精密慢刀伺服车削**（单点金刚石车刀、7050 铝）实验，转速本来就极低，拿去常规车削会出事故；② 另一条数值在原文里是**转引**（图 9 标注的是文献[85]的结果）；③ 问题问“智能体”，候选里的“智能体”是**强化学习产线调度 agent**（把工人抽象成智能体），与 LLM 智能体不是一回事。 |
| 根因   | 提示词只要求“每条结论挂引用”，没有要求“引用时保留适用语境”。引用校验能把“编造”挡掉，**挡不住“正确但被误用”**——这类问题只有人读的时候才发现（也说明“代码校验 + 人工抽读”两道都要有）。                                                                                                                                                          |
| 改法   | `ANSWER_PROMPT` 规则 1 补两条：引用具体数值/参数/做法时**必须带原文适用语境**（材料/机床/工况）；术语可能**不同义**时必须显式说明差异，不得当同一概念回答。加测试 `test_answer_prompt_requires_context_fidelity`。                                                                                                                          |
| 验证   | 174 passed；提示词改动属“下次真跑才能量出效果”的那类，登记为待验证项（下轮真实使用时重点看数值条目有没有带语境）。                                                                                                                                                                                                                              |
| 影响面 | 答案会更长一点（每条数值多一句语境），但这是“能不能被误用”的分界线。**普适教训**：引用校验能保证“没编”，不能保证“没用错”；后者只能靠提示词约束 + 人读关键条目。                                                                                                                    |

### T36 参考文献列表段：标记对了，但第一版判据把正文标成了文献表

| 项     | 内容                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 现象   | 第 22 周真跑两次出现“参考文献列表页被当候选”（一次模型自己拒绝、一次进了四段）。所以在建索引时给片段打 `is_reference` 标记、检索默认排除。**第一版判据直接踩雷**：2501 个片段里标出 **664 条（26.6%）**，单篇最多 76 条，而且散布在正文各页——把综述的正文页也标了。                                                                                                                                                                  |
| 根因   | 判据用的是「`[数字]` 紧跟字母/汉字」+「密度 ≥0.5 条/百字」。中文综述正文里"XING Q Q 等[18]提出…"这种句子满篇都是，密度轻易超标——**特征是"正文里也会出现的东西"，于是判据变成了噪声源**。第二版只留**书目专属**特征：`[J]/[C]/[M]` 类型标识、`doi.org/10.`、`et al`/`等.`、英文"编号. 姓, 首字母."、`[CrossRef]`。                                                                                                                          |
| 改法   | ① 判据换成书目专属特征（≥4 条）；② `et al` 不再要求点号紧跟（PDF 抽取常变成 `et al .`，实测某页 10 个片段一个都没标上）；③ 检索层加**页级多数表决**：同一 `(文件, 位置)` 下过半片段被标记就整页按文献表处理（文献表常被切得很碎，逐片段判不出来）。④ 留 `--include-references` / `exclude_references=False` 复现路径。                                                                                                                |
| 验证   | 标记降到 **657/2501**（含页级表决），命中页集中在论文末尾（如某综述：全文 1~27 页、命中 18~27 页）；三篇英文论文也被覆盖（Machines2026 命中 30~31 页 = 末页）。复跑 Q2：**参考文献片段彻底不在 top-5 里，内容片段一条没少**。新增 8 条离线测试（判据正/负例、`et al .`、页级表决、检索排除）。                                                                                    |
| 影响面 | 约 26% 片段默认不进候选——对"综述密集"的语料是合理的（这些论文的文献表本来就占两三成），且**它是显式开关**，要复现"含文献表"的检索随时可以。**遗留**：有些文献页每个片段只剩 1~2 条特征，页级表决也补不上，根治要在解析层按整页判定再下传（已登记）。                                                                                                                  |

### T37 Web 首跑第一条：进度条压根没渲染

| 项     | 内容                                                                                                                                                                                                                                                                                                       |
| ------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 现象   | 使用者按 checklist 第 2 条复验时反馈"好像没有进度条"：整个提问过程界面只有输入框变灰，看不到"检索 / 盘点 / 作答"走到哪一步。而 SSE 事件序列在离线冒烟里是**验证过**的（`start → load → retrieve:start/done → plan → answer → result`）。                                                                    |
| 根因   | `stepLine()` 里 `const line = el("li")` 之后只做了 `steps.set(key, line)`——**写进 Map，却从没 `appendChild` 到 DOM**；函数签名里连那个 `<ul>` 都没传进来，等于这段渲染代码从来没接上。                                                                    |
| 改法   | `stepLine(stepList, steps, event)`：补 `stepList.appendChild(line)`，调用处传 `ctx.stepList`。      |
| 验证   | 手工复跑：逐步亮起（`✓ 检索资料库 · 第 1 轮 · 命中 10 条 · 0.05s` → `◐ 盘点信息缺口` → `◐ 组织答案`）。**这条没有自动化测试兜**，所以"前端无自动化测试"从低优先升为待补项。      |
| 影响面 | **"协议通过"不等于"界面画出来了"**：离线测试覆盖的是事件序列与数据字段，DOM 写入这一步谁都没测。同类风险还有引用展开与候选折叠两块，登记为待补（要么加 JS 测试，要么把 `handleEvent` 的 DOM 写入抽成可单测的纯函数）。 |

### T38 Web 首跑第二条：追问判据把独立小问题当成追问

| 项     | 内容                                                                                                                                                                                                                                                                                                                                                                     |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 现象   | 使用者问完“AI 辅助工艺编制怎么做？”（**正好 12 字**）后问“异星工厂是什么”，界面提示"本次检索词带上了上一问"，日志里那行是 `"AI 辅助工艺编制怎么做？ 异星工厂是什么"`——**候选整批跑到数字孪生 / 产线调度那边**，与所问毫无关系。                                                                          |
| 根因   | 判据第一版是"长度 ≤ 12 或含指代词"。"**句子短**"这种特征在追问里会出现、在独立小问题里也会出现，拿它当判据就是给自己造噪声——与 T31/T36 是同一条错误：特征没挑"目标里几乎不会出现、噪声里才有的"。                                                                                                                                                                          |
| 改法   | 去掉纯长度判据，改成**指代词 / 追问标记词**（它、他们、这个、那些、上述、还有、继续、展开说…）**或 6 字以内的极短句**（"还有呢？""为什么？"）：`_ANAPHORA` / `_CONTINUATION` / `FOLLOW_UP_MAX_CHARS = 6`。                                                                                                                                                                  |
| 验证   | 新增回归测试 `test_follow_up_heuristic_does_not_swallow_short_standalone_questions`（把首跑那句原样钉住）+ 正反例各 5 个；`pytest` 213 passed。                                                                                                                                                            |
| 影响面 | 判据仍会误伤（"那优化呢？"里的"那"没进表），但**界面上拼了什么、开关在哪都摆着**——判错的成本被界面兜住了。这也解释了这个设计为什么值得把 `retrieval_query` 显示出来：判据不可能全对，可解释性才是兜底。**遗留**：先用真实提问看漏拼多不多，再决定要不要加更重的判定（已登记）。                              |

### T39 修 T37 的时候，把调用处漏了（改签名的经典摔法）

| 项     | 内容                                                                                                                                                                                                                                                                                                                                                                                   |
| ------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 现象   | 修完 T37、重启服务并强刷浏览器后，**提问的瞬间**界面就报 `连接中断：TypeError: Cannot read properties of undefined (reading 'stage')`——服务器那头其实照常跑完了（对话日志里多了记录），坏的只有界面。                                                                                                                        |
| 根因   | 给 `stepLine` 加参数（`stepList`）时**只改了函数定义，没改调用处**：调用还是 `stepLine(ctx.steps, event)`，于是形参 `steps` 拿到事件对象、`event` 是 `undefined`，直到执行 `event.stage` 才炸。JS 不会因为实参个数不匹配报警——**这类错误是静默的，直到落到具体属性访问**。                                              |
| 改法   | 调用处补全：`stepLine(ctx.stepList, ctx.steps, event)`。                                                                                                                                                                                                                                                               |
| 验证   | **变异测试两处**（T13 的做法）：把 `stepList.appendChild(line)` 删掉 → 冒烟报 `T37：进度行没有插进 DOM`；把调用处改回旧写法 → 冒烟报 `TypeError: Cannot read properties of undefined (reading 'stage')`，与现场一致。两处随后用 `apply_patch` 还原，复跑全绿。                                                            |
| 影响面 | 同一块功能**连续两次**坏在"画出来"这一步（T37 少画、T39 画炸），说明缺的不是"更小心"，而是**一层不依赖浏览器的 DOM 测试**。现已补上：`tests/frontend_smoke.mjs`（`makeEl()` 迷你 DOM，把 `index.html` 的内联脚本当函数体执行）+ `tests/test_web_frontend.py`（没装 node 就 skip）。它覆盖进度条渲染、四段与空段说明、三种引用状态点开看原文、候选折叠，以及**真实 SSE 分帧（含跨 chunk 的半截帧）到渲染的端到端**。**"协议通过"不等于"界面画出来了"**，这条从此有测试兜。 |
