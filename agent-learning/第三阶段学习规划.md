### 关键术语速查（本阶段新出现的词）

| 术语 | 一句话解释 |
| ---- | ---------- |
| **MCP** | Model Context Protocol：让 AI 应用（Codex / Claude 等）以统一方式调用外部工具的协议 |
| MCP server / client | 你写的"提供工具的一方"是 server；Codex 这类"调用方"是 client |
| **tool** | server 暴露给模型的函数（名字 + 参数 schema + 注释）；模型据此决定调不调、怎么调 |
| stdio 传输 | server 作为本机子进程、通过标准输入输出通信（**不占端口、不出网络**）。另有 sse / streamable-http |
| MCP Inspector | 官方调试界面（`mcp dev`），不用写客户端就能手动点着调工具 |
| `ToolAnnotations` | 工具元信息，**`read_only_hint` / `destructive_hint` / `open_world_hint`** —— 把"只读"写进协议而不是嘴上说 |
| 文本蕴含判断 | "原文里有没有说这件事"——一个**非本领域的人也能做**的判断（对比："这个结论对不对"需要专家） |

## 一、阶段定位与四个目标

前两阶段解决的是：**怎么跑起来**（第一）→ **怎么让它真有用**（第二：能维护、能检索、能服务科研、能给别人用）。
第三阶段解决的是：**怎么让"别人"和"别的 Agent"也能用，并且敢用**。

区别在于"使用者"变了：前两阶段的使用者是人（自己、以及打开浏览器的人），
第三阶段的使用者**还包括别的 AI 应用**——它们会自己决定调不调你的工具、调几次。这带来三个新问题：

1. **接口问题**：能力要能被程序调用（schema、错误约定、边界），不能只靠一个网页；
2. **信任问题**：别人（和别的 Agent）凭什么信你的答案？第二阶段结尾认定最硬的限制就在这里；
3. **闸门问题**：自动调用意味着**成本可能失控**——一次问答 2~7 分钱，被循环调用就是事故。

四个目标**按依赖顺序**推进：

| 顺序 | 目标 | 覆盖周次 | 为什么排这个位置 |
| ---- | ---- | -------- | ---------------- |
| **H1** | 结清地基 | 第 25~26 周 | MCP 层要直接复用检索与问答。先把登记的遗留、夹具与前端测试缺口清掉，否则新接口建在晃动的地上（与 G1 同样的道理） |
| **H2** | 把能力做成标准接口（**MCP server**） | 第 27~30 周 | 第 12 周就写下"只会用别人写的 MCP，试着自己写一个"——这是它落地的一步，也是"从自己用到别人用"最实的一步 |
| **H3** | 让结论**可被独立核对** | 第 31~34 周 | 第二阶段认定最硬的限制：没有本方向的人能核对专业正确性。这个目标把"专业判断"降级成**文本蕴含判断**，让外行也能核一层 |
| **H4** | 交付与复盘 | 第 35~36 周 | 界面补"我能答什么"、结果可导出、阶段复盘 |

**一句话的取舍**：本阶段**不追求更聪明的回答**（那要换模型或微调），追求的是
**同一套能力被更多人用、被更严格地核对、被更清楚地说明**。

## 二、技术路线与选型（含已核实的前提）

### 2.1 五个已核实的前提（2026-10-12 实测，不是查教程）

| 前提 | 核实结果 | 对设计的影响 |
| ---- | -------- | ------------ |
| MCP 的 Python SDK 现在什么版本、API 稳不稳 | **`mcp 2.2.0` 可装**（Python 3.13.14）。**2.x 把 `FastMCP` 改名为 `MCPServer`**（`from mcp.server.mcpserver import MCPServer`）；网上**多数教程还是 1.x 的 `mcp.server.fastmcp`**，照抄会直接 `ModuleNotFoundError` | 选型锁 2.x；本项目文档里必须写清这次改名，否则以后自己照旧教程改代码会白折腾半天 |
| MCP 工具能不能**离线测试** | 能：`await server.list_tools()` 与 `await server.call_tool(name, args)` 都是协程，`call_tool` 返回 `CallToolResult`（含 `structured_content`）；**不需要起传输、不需要网络** | 验收可以要求"**每条工具都有离线测试**"，与现有 220 条 pytest 同一套跑法、CI 里自动跑 |
| "只读"能不能写成可断言的字段 | 能：`ToolAnnotations(read_only_hint=True, open_world_hint=False)`，字段在 `mcp.types.ToolAnnotations` | "只读边界"从口头约定变成**协议字段**，测试里可以断言 |
| 开发期怎么手动调工具 | `mcp[cli]` 装上后有 `mcp dev`（MCP Inspector）、`mcp run`、`mcp version` | 不用自己写调试客户端；接线之前先拿 Inspector 过一遍 |
| 传输方式怎么选 | `server.run(transport="stdio")` **是默认值**，另有 `sse` / `streamable-http` | 本阶段**只用 stdio**：本机子进程、不占端口、不出网络 —— 与第二阶段"不做云部署与公网访问"一致 |

> 这两条**不是抄来的**：2.x 那个改名是探针撞出来的（我第一次按教程写 `from mcp.server.fastmcp import FastMCP`，
> 收到一句明确的迁移提示），`list_tools`/`call_tool` 是异步、`read_only_hint` 是蛇形命名这两条也是实测才知道。
> 记在这里，省得下次再撞。

### 2.2 选型表

| 需求 | 选定方案 | 依据 | 备选 / 排除 |
| ---- | -------- | ---- | ----------- |
| MCP SDK | **`mcp` 2.2.0**（官方 Python SDK） | 实测可装、可注册工具、可离线调用、自带 `mcp[cli]` 调试工具 | ❌ 手写 JSON-RPC（重复造轮子且易错）；❌ 停在 `mcp<2`（没有理由用旧 API） |
| 传输 | **stdio**（`server.run()` 默认） | 与第 11 周接 filesystem MCP 的写法同族（`~/.codex/config.toml` 里 `command` + `args`），已证明可行 | ❌ sse / streamable-http：本阶段不需要常驻网络服务 |
| 能力来源 | **直接复用** `rag/retriever.py` + `rag/review_qa.py` + `web/service.py` 的编排 | 第二阶段的成果，不重写内核 | ❌ 复制一份实现（T43 的教训：同一件事两份实现必然漂移） |
| 工具粒度 | 三个：`search_corpus`（只读、不花钱）、`read_chunk`（只读、不花钱）、`review_question`（**花钱，默认关**） | 前两个是"让别的 Agent 能查我的语料"；第三个是完整问答，必须有闸门 | ❌ 只暴露 `review_question`（别的 Agent 会拿它当免费检索用） |
| 成本闸门 | `review_question` 需**显式开启**（环境变量 / 配置），且**每次返回花费与调用次数** | 一次问答 2~7 分钱，被自动循环调用就是事故 | ❌ 靠提示词"请省着调用"（那是请求，不是闸门） |
| 核对工件 | **Markdown 清单**：一条结论 + 它引用的原文片段 + 一个问题"原文支持这句话吗？（是/否/不确定）" | 让**非本领域的人**也能核"表述与原文是否一致" | ❌ 指望找专家逐条读（第二阶段已证明不现实），❌ 让模型自己核（那是自证） |

### 2.3 成本与内存策略（延续第二阶段，另加两条）

1. **只读工具不花钱**：`search_corpus` / `read_chunk` 全程本地（BM25 + 向量检索 + 读盘），
   这是"给别的 Agent 用"最合适的入口——**它们可以随便调**；
2. **花钱的那个必须显式开**：`review_question` 默认不注册（或注册但立即返回"未开启，附开启方法"），
   开启后每次调用在返回值里**带上花费与累计**，让人和 Agent 都能看见；
3. **检索器单例复用**：MCP server 是长驻进程，索引只加载一次（第二阶段冷启动 3.3s → 之后 0.01s 的先例）；
4. **内存**：不引入新模型（沿用 fastembed 后端），MCP 进程与 Web 进程不同时跑重活（延续 2.3 的内存纪律）。

## 五、明确不做（延续第二阶段，另加三条）

- **不做云部署与公网访问**（延续）：MCP 只走 stdio，本机子进程；
- **不做多用户鉴权与账号体系**（延续）；
- **不做模型微调 / 自训 embedding**（延续，算力不允许）；
- **不做实时联网检索**（延续：补资料仍是"离线下载 → 入库"）；
- **不做移动端适配**（延续）；
- **不引入 Docker 与独立数据库服务**（延续；嵌入式方案不算）；
- **不做写操作**（新增）：MCP 暴露的工具**一律只读**，不提供"改文件 / 写库 / 删除"；
- **不追求回答更聪明**（新增）：本阶段不加模型、不加"自我反思"链路——想清楚了再动，
  否则成本与不可解释性一起涨；
- **不用第二个模型核对答案**（新增）：模型自证不算独立核对，宁可承认"这一层核不到"。

## 六、风险与降级预案

| 风险 | 可能性 | 影响 | 预案 |
| ---- | ------ | ---- | ---- |
| MCP 2.x API 仍在变（2.2.0 是新版） | 中 | H2 中途返工 | 只用最稳定的三件事（`MCPServer` / `@server.tool()` / `run()`）；把撞到的差异**记进笔记**而不是默默绕开；必要时锁版本 |
| `review_question` 被别的 Agent 反复调用 | 中 | **成本失控** | 默认不注册 + 显式开启 + 每次返回花费 + 同会话次数上限；测试里用计数假调用断言"未开启时不发请求" |
| 补资料下载不到（四类里最缺的那类） | 中高 | H3 部分受阻 | 沿用 `eval/语料来源-*.md` 的"已知死路"记录法；补不到就如实记"试过什么、卡在哪"，不拿别的方向凑数 |
| 核对只做到"文本蕴含"这一层，被误解成"专业正确" | 中 | **表述风险** | 核对工件与结论表里都写死一句："本核对只回答'原文有没有这么说'，不回答'这个结论对不对'" |
| 语料扩到 100~500 篇后检索变差 | 中 | 数字全变 | 建库后**必须重跑检索评测**（沿用第二阶段"换语料就要重测"的规矩）；必要时调 `top_k` / 每篇上限 |
| 每周 5 小时达不到 | 中 | 阶段延期 | 沿用降级顺序：H4 可裁（界面与导出），H2 可降到"单工具最小实现"，**H3 的核对不能裁**（它是本阶段唯一"新"的东西） |

## 七、文档约定（沿用 + 新增）

- 每周一篇笔记（`第25周笔记.md` …），格式：一句话结论 / 关键实现 / 实测记录 / 踩坑 / 我的复盘；
- 技术债进 `工程化改造记录.md`（**T44 起**），每条"现象 → 根因 → 改法 → 验证"；
- MCP 相关文档放 `notes-qa/mcp_server/README.md`（接线方法、工具清单、成本闸门）；
- 核对工件与结论表放 `notes-qa/eval/`；
- 换语料、换判据、改口径 → **必须重跑并改数字**，旧数字要标"（旧口径）"。
