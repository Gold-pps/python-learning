# 第 3 周笔记：让 Agent 学会使用工具

日期：约 2026-09-09
主题：用 `@function_tool` 把 Python 函数交给模型调用

> **补写说明**：本笔记为 2026-09-15 补写。内容依据 `学习Agent规划.md` 第 3 周、
> `学习进度.md` 的"第 3 周"章节与脚本 `02_agent_with_tool.py`、数据文件 `python-base/students.csv` 整理。

## 一句话结论

工具就是"写给模型看的函数说明书"：模型根据函数名、docstring 和参数类型**自己决定**调不调、传什么参数；
Python 端真正执行，再把结果回给模型组织回答。
这就是 `模型决定调用工具 → 代码执行 → 结果返回模型` 的完整循环。

## 1. 本周注册的三个工具

| 工具名 | 参数 | 返回 | 用来验证什么 |
| --- | --- | --- | --- |
| `get_beijing_time()` | 无 | 当前北京时间字符串 | **模型不可能凭空知道**的信息（实时时间） |
| `count_students_rows()` | 无 | `students.csv` 数据行数（不含表头），当前为 `11` | 读本地文件、做计算 |
| `find_student_home(name)` | `name: str` | 该学生的家乡，找不到返回"未找到该学生" | **带参数**的工具调用 |

```python
@function_tool
def find_student_home(name: str) -> str:
    """在 python-base 目录的 students.csv 中查找指定学生的家乡，找不到就返回提示。"""
    print(f"[工具被调用] find_student_home(name={name})")
    csv_path = Path(__file__).resolve().parent.parent / "python-base" / "students.csv"
    for line in csv_path.read_text(encoding="utf-8").strip().splitlines()[1:]:
        student, home = line.split(",")
        if student == name:
            return home
    return "未找到该学生"
```

要点：

- **docstring 就是工具说明**，模型靠它判断什么时候该调用；
- 参数的类型标注（`name: str`）会被转成 JSON Schema；
- `print` 只是给人看的日志，不影响模型——但它是判断"工具到底被调用没有"的最直接证据。

## 2. 完整循环长什么样

```text
用户：cain 的家在哪？
  ↓
模型读到工具说明书 → 决定调用 find_student_home(name="cain")
  ↓
Python 执行 → 打印 [工具被调用] find_student_home(name=cain) → 返回 "bible"
  ↓
结果回传模型 → 模型组织自然语言回答
  ↓
输出：根据查询结果，Cain 的家乡是 Bible。
```

验证成功的关键判据：**终端出现了 `[工具被调用]`**。没出现，说明模型这次没调工具——
要么是指令没说清，要么是问题本来就不需要工具。

## 4. 工具说明书的 JSON Schema

`@function_tool` 会把函数签名翻译成类似下面的结构交给模型。第 9 周写 `tools.py` 时，
`additionalProperties: false`、`required` 这些字段就是从这里理解的：

```json
{
  "name": "find_student_home",
  "description": "在 python-base 目录的 students.csv 中查找指定学生的家乡，找不到就返回提示。",
  "parameters": {
    "type": "object",
    "properties": {
      "name": {"type": "string", "description": "学生的姓名"}
    },
    "required": ["name"],
    "additionalProperties": false
  }
}
```

三个字段的作用：

- `required`：哪些参数必须给；
- `additionalProperties: false`：不许模型自己编造额外参数（SDK 默认就会加上）；
- `description`：模型判断"该不该调用"的主要依据，也是**唯一能靠写文字提升工具命中率的地方**。

## 5. 指令（instructions）的写法

```python
instructions=(
    "你是一个中文助手。当用户询问当前时间时，"
    "你必须调用 get_beijing_time 工具获取真实时间，再简洁回答。"
    "当需要查看本地文件、统计行数或读取文件内容时，"
    "你必须调用对应工具获取真实数据，再简洁回答。"
    "若问题中没有对应的工具，则尝试所有工具"
)
```

- 用"**必须调用**"这类硬约束，能显著提高工具命中率；
- 但最后一句"若问题中没有对应的工具，则尝试所有工具"是**反例**：它让模型在无关问题上也去试工具，
  既浪费 token 又可能答偏。第 9 周做 `notes-qa` 时改成了"没有依据就明确说没有找到"，不再鼓励乱试。

## 6. 坑与注意

| 坑 | 说明 |
| --- | --- |
| 必须走 Chat Completions 路径 | 本周仍靠 `set_default_openai_api("chat_completions")`，不能使用 Responses 专属的工具能力 |
| CSV 解析不够健壮 | `line.split(",")` 在行内逗号超过 1 个时会抛 `ValueError`，属于"工具不该直接把异常抛给 SDK"的反面教材（第 9 周起统一改为返回结构化错误） |
| 日志格式不统一 | `find_student_home` / `count_students_rows` 打印带函数名，`get_beijing_time` 只打印 `[工具被调用]`，会影响后面按关键词做评估的稳定性 |
| 环境说明已过期 | 脚本 docstring 里还写着"在 miniconda base 里运行"，当前环境是仓库根目录 `.venv`（Python 3.14.4） |

## 7. 复盘（补写时整理）

- **最有价值的一次观察**：同一个回答里，哪些字是模型"生成"的、哪些字是工具"查"出来的——
  这决定了后面 `notes-qa` 的设计原则"只依据工具返回的内容回答"；
- **工具设计的一句话原则**：函数名 + docstring 写得越明确，命中率越高；
  想让模型少乱调，靠的是**否定式的指令**（没有依据就说没有），而不是列一堆"什么都能干"的工具；
- **这一周的循环图**是后面所有内容的地基：护栏加在循环的两端，评估在循环外统计通过率，
  成本分析看的也是同一份 usage。
