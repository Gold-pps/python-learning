## 2. 关键设计

### 2.1 延迟导入：让"主环境"和"RAG 环境"能共用一个包

`rag/` 下有三种模块，依赖完全不同：

- `chunk.py` / `parsers.py` / `chunker.py`：纯 Python + `pypdf` / `python-docx`；
- `embedder.py` / `index.py`：要 torch 或 onnxruntime，只在 `.venv-rag` 里跑。

**问题**：如果 `embedder.py` 顶层 `import torch`，主环境 import 就挂；
56 条测试里凡是碰到 `rag` 的都会红。

**解法**：`import torch` 写在 `_load()` 里，不在模块顶层。
验证：主环境 `from rag.embedder import Embedder` 通过，且 `'torch' in sys.modules` 为 `False`。

**代价**：`index.py` 里仍然要 `from .embedder import ...`，但只在 `_cli()` 里做。
真正需要 torch 的路径只有一条：`python -m rag.index build`。

### 2.2 `constants.py`：断开一条隐式的依赖链

`parsers.py` 需要 `MAX_FILE_BYTES`，它原本从 `tools.py` 拿；
`tools.py` 又 `import config`；`config.py` 又 `from agents import ...`。

**结果**：`rag` 想读一个整数常量，被迫拖入 `openai-agents`。
`.venv-rag` 里没装它，直接 `ModuleNotFoundError`。

**改法**：把 `MAX_FILE_BYTES` 抽到 `constants.py`——**不 import 任何项目内模块，也不 import 第三方库**。
两边都 `from constants import MAX_FILE_BYTES`。

**普适教训**：**一个模块的依赖面由"它 import 了谁"决定，不由"它实际用到什么"决定**。
一个常量被一个重型模块 re-export，就会把它绑在重型模块上。

### 2.3 增量跳过：hash 对比，不是 mtime

`_load_old_vectors()` 读旧 `chunks.jsonl`，按 `hash -> Chunk` 建表；
新的 chunks 里凡是 hash 命中旧表的，直接从 `vectors.npz` 里搬向量。

**为什么不用 mtime**：文件"改了但内容没变"（换行、存盘）不必要重算；
内容变了但 mtime 没变（罕见但可能）会漏算。
hash 是内容级判断，两端都稳。

**实测**：22 篇首次 15.58s → 再次 0.08s（快 195 倍）。
**但这不是核心收益**：核心是"重建"这个动作从"要不要跑"变成"随手跑"——
以前重建索引要考虑耗时，现在没有成本，可以每次改完 chunker 都重建。

### 2.4 双后端：**不是"有 GPU 就用 GPU"**

实测（22 篇，431 片段，Windows + RTX 3050 + 15.7 GB）：

| 后端                      | 冷启动     | 增量重建 | 内存增量 |
| ------------------------- | ---------- | -------- | -------- |
| `bge`（torch + CUDA）     | 15.58s     | 0.08s    | ~1116 MB |
| `fastembed`（ONNX + CPU） | **14.82s** | 0.08s    | ~941 MB  |

**注意**：这两个数字都包含"模型加载"。
**单独测小批量（60 条短文本）**：
- `bge` 冷启动 13.08s / 热启动 0.021s；
- `fastembed` 冷启动 **0.33s** / 热启动 0.035s。

**结论**：
- torch 加载 CUDA 上下文要十几秒，ONNX 加载只要零点几秒；
- 对**小批量**（几十到几百 chunk，本项目典型规模）：**fastembed 更快**；
- 对**大批量**（几千 chunk 以上）：`bge` + CUDA 才划算（GPU 推理吞吐是 CPU 的数倍）。

**这条推翻了我一开始的直觉**。原本以为"有 GPU 就用 GPU"是理所当然——
实测说明"加载成本"在短任务里是主导项，GPU 的优势要批量足够大才盖过它。

**交叉验证**：两个后端跑同一批文本，向量点积（已归一化，等价余弦）**全为 1.0**。
说明 BGE 的 torch 版与 ONNX 版实质等价，两个后端可以互相校验。

### 2.5 索引产物三件套

```
data/index/
├── chunks.jsonl   每行一个 Chunk（顺序与 vectors 行号一致）
├── vectors.npz    np.savez 格式，'vectors' 键，float32, shape=(N, 512)
└── meta.json      模型名、维度、chunk 数、文件数、构建时间
```

`chunks.jsonl` 用 JSONL 而不是 pickle，理由是**可读、可 diff、跨语言**。
将来做 Web 界面时可以直接读它展示来源。

## 3. 踩坑

1. **`rag` 被迫拖入 `agents`**：见 2.2。**修法不是"在 .venv-rag 里也装 agents"，
   而是断开依赖链**。第一种是掩盖问题，第二种是解决问题。
2. **import 位置错了三次**：
   - 第一次：把 `from constants import ...` 夹在常量定义中间 → ruff I001；
   - 第二次：挪到 import 区但顺序不对 → 还是 I001；
   - 第三次：`ruff check --fix` 自动修好。
   **教训**：手写 import 顺序靠不住，让 ruff 修。
3. **PowerShell 里 `..\..\.venv-rag\Scripts\python.exe` 直接写会报"找不到"**：
   要用 `& "路径"` 显式调用。这是 PowerShell 的安全策略，不是路径错。
4. **PowerShell 里 `-c "长字符串"` 会被转义弄坏**：
   `print(f'{r["key"]}')` 里的 `"` 会被 PowerShell 吃掉。
   **修法**：超过两三行的脚本一律写成临时 `.py` 文件再跑，不塞在 `-c` 里。
5. **内存测量的污染**：第一次测 fastembed 的"基线"是 1178 MB——
   因为 bge 的模型还挂在同一个进程里。要拿干净数字要在两个独立进程里测。
   本周**没做这件事**，笔记里如实标注。
6. **规划写"30 篇"，实际只用 22 篇**：因为 `agent-learning/` 下只有 22 篇 `.md`。
   431 个片段已经足够验证增量与双后端，**笔记里如实标注差 8 篇**。
