## 一、总体结论

**学习成果本身是扎实的**：12 周计划确实落地了，每周有可运行产出，项目有真实的安全加固（路径穿越、junction 逃逸、timeout），评估脚本不是走过场。我实测 `--unit-only` 得到 12/12，与文档声明一致。

**主要不足集中在"维护性"而不在"学习质量"**，可以归为 5 类：

| 类别 | 严重度 | 一句话概括 |
| --- | --- | --- |

## 四、环境与可复现性（🔴 高优先）

### 4.1 Python 版本声明错误（真实矛盾）

- **文档三处都写"Python 3.10+"**：`README.md:111`、`requirements.txt:4`、`学习Agent规划.md:48`。
- **实际代码要求 ≥3.12**：
  - `notes-qa/main.py` 用 `asyncio.timeout()` → 需 **3.11+**；
  - `notes-qa/eval_cases.py` 用 `Path.is_junction()` → 需 **3.12+**。
- **实测环境**：`.venv` 里是 **Python 3.14.4**。
- **影响**：别人（或未来的你）按文档装 3.10，`main.py` 和 `eval_cases.py` 会直接 `AttributeError`，且报错点很隐蔽。
- **建议**：文档统一改成"Python ≥3.12"；或在代码里加版本断言 `assert sys.version_info >= (3, 12)`。

### 4.2 依赖清单与实际环境漂移

- `requirements.txt` 钉的是 `python-dotenv==1.2.1`、`requests==2.33.1`；
- 实际 `.venv` 里是 `python-dotenv 1.2.3`、`requests 2.34.2`。
- 另外 `requirements.txt` 的注释写"agent/ 学习项目"（目录早已改名 `agent-learning/`），还写着"Miniconda 已于 2026-09-08 卸载"这类历史说明。
- **已处理（2026-09-15）**：按 `.venv` 实际版本重写为 `python-dotenv==1.2.3`、`requests==2.34.2`，
  注释里的目录名改为 `agent-learning/`，Python 版本改为 ≥3.12，并把历史环境说明整理到文件末尾的"说明"一节。

### 4.3 装环境有三套互相矛盾的命令

| 出处 | 命令 |
| --- | --- |
| `README.md` 快速开始 | `uv venv .venv` + `uv pip install ...` |
| `学习进度.md` | `uv venv` + `uv pip install --python .venv/bin/python ...` |
| `requirements.txt` | 注释说"新建 venv 后执行 `pip install -r requirements.txt`" |

- **已处理（2026-09-15）**：`README.md` 与 `AGENTS.md` 统一用 `uv`；`requirements.txt` 顶部写明了
  `uv pip install -r` 与 `python -m venv` + `pip install -r` 两种等价装法。

### 4.4 缺少工程化配置

- 没有 `pyproject.toml` / `uv.lock` → 依赖无法完全锁定；
- `.gitignore` 里已经有 `.mypy_cache/`、`.pytest_cache/`，说明当初打算用 mypy/pytest，但仓库里**没有任何 mypy / ruff / pytest 配置**；

- **建议**（性价比从高到低）：① `pyproject.toml` + 把 `eval_cases.py --unit-only` 挂成 pre-commit 或简单脚本；② 加 ruff 做格式/静态检查；③ 有余力再接 GitHub Actions。

## 六、评估体系的不足（🟡 中优先）

### 6.1 `eval_cases.py` 会在仓库根留下探针文件

- `unit_read_note_blocks_symlink_escape` 和 `unit_list_notes_skips_link_escape` 用 `config.NOTES_ROOT.parent`（即**仓库根** `python-learning/`）作为探针目标目录，会临时创建：
  - `python-learning/_probe_secret.md`
  - `python-learning/_probe_linkdir_target/`（及其中的 `_probe_outside.md`）
- 正常路径有 `finally` 清理，但**一旦脚本被 Ctrl-C 或崩溃中断**，这些文件就留在仓库根，且不在 `.gitignore` 里，会直接出现在 `git status` 中。
- 同理，`_probe_big.md`（1MB）、`_probe_lines.md` 等若中断会留在 `agent-learning/`，被 `list_notes` 当成真笔记列出。
- **实测证据（2026-09-15）**：本次评审跑完 `python eval_cases.py --unit-only`（U6 显示 PASS）后，
  `git status` 里真的多出一个未跟踪文件 `agent-learning/_probe_linkdir.md`，指向已被删除的
  `python-learning/_probe_linkdir_target`，是个断链。
- **根因（已定位，待修）**：U6 的 `finally` 里用 `os.rmdir(link)` 删除符号链接。
  Linux 上 `rmdir` 对符号链接返回 `ENOTDIR` 失败，抛出的 `OSError` 又被 `except OSError: pass` 吞掉，
  于是链接被留下——**不是"中断才残留"，而是正常路径就会残留**。正确写法是 `os.unlink(link)`。
- **建议**：① 把 `os.rmdir` 改成 `os.unlink`；② 探针统一放到 `tempfile.mkdtemp()` 下的临时目录，
  用 `atexit` 或 `try/finally` 兜底清理；③ 在 `.gitignore` 加 `_probe_*` 作为双保险。

### 6.2 评估用例偏少且存在"题面污染"

- 模型评估只有 3 条（M1/M2/M3），且 `项目设计.md` 第 13 节自己承认：M1 的题目原文被写进第 9 周笔记，导致"搜到的是题目本身而不是答案"。
- **建议**：M1 的题面换个措辞（或用 `学习进度.md` 里没有原句的问法）；每条用例的目标文件改为断言"引用文件集合"，而不是只看一个文件名。

### 6.3 `07_evaluate_agents.py` 的关键词检查过于脆弱

- `expected` 里出现 `"9"` 这种单字符期望词——脚本输出里任何含 `9` 的字符（如 token 数 1299）都会让用例 PASS，属于隐藏的假阳性。
- 同时 `expected` 里有 `"cain"`、`"bible"` 这种"答案词"，一旦 CSV 数据变动，用例就静默失效。
- **建议**：单字符期望词换成完整短语；把"数据词"改为断言工具被调用的日志标记。

### 6.4 两套评估风格并存

- `python-base/` 用 **pytest**，`agent-learning/notes-qa/` 用**手写 `UNIT_CASES` 列表**。
- 手写版的好处是零依赖、能打印中文表格；坏处是没有 fixture、没有参数化、发现失败的精度低。
- **建议**：要么统一到 pytest（`pytest -q` 输出对 CI 更友好），要么在 README 里说明"两套并存是有意为之"。

### 6.5 评估没有常态化

- 目前靠手动跑。12 周计划第 4 节写"每周至少留下一个可运行的产出"，但没有"每周回归跑一次评估"的机制。
- **建议**：用 IDE 的定时任务（automations）或系统 cron，每周固定跑 `eval_cases.py --unit-only` 并记录结果；模型评估留在低谷时段手动跑一次。

## 七、仓库卫生与安全（🟡 中优先）

### 7.1 学习仓库里塞了 92MB 的 PPT

- 根目录有 4 个 `.pptx`（`毕业答辩-*.pptx` 各 ~46MB、`组会汇报*.pptx`）和 1 张截图；
- `.git` 目录已经 **93MB**，其中绝大部分是 PPT 的历史版本。
- **影响**：clone 极慢；`git log` 里出现"组会ppt提交""空白模板"这类与学习无关的提交，历史不干净；换电脑时拉仓库体验很差。
- **建议**（任一）：① 把 PPT 移到仓库外（网盘/单独的 presentations 仓库）；② 用 Git LFS；③ 若必须保留，至少加 `.gitattributes` 并把历史里的旧版本用 `git filter-repo` 清掉（属破坏性操作，需先备份）。

### 7.2 残留的第二份 `.env`

- 工作区存在 `agent/.env`（52 字节），内容与 `agent-learning/.env` 同为 API Key 副本；
- `agent/` 目录里**只有这一个文件**，是历史路径遗留；
- `.gitignore` 里写的却是 `agent/.env`、`agent学习/.env` 这两个**已经不存在**的路径（真正生效的是全局的 `.env` 规则）。
- **影响**：多一份密钥副本就多一个泄露面；`.gitignore` 规则与现状脱节，后人看不懂。
- **建议**：删掉 `agent/` 目录；`.gitignore` 里把两条历史路径换成 `agent-learning/.env`（或保留全局 `.env` 并删掉冗余项）。

### 7.3 明文 API Key 未处理

- 第 12 周笔记"遗留待办"里自己列了：`~/.codex/config.toml` 里的明文 API Key，优先级"中"，**至今未做**。
- **建议**：改成环境变量注入（`env = { DEEPSEEK_API_KEY = "$DEEPSEEK_API_KEY" }`）；顺带做一次"如果这个 Key 泄露了怎么办"的演练（去平台吊销重签）。
