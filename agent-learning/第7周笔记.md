# 第 7 周笔记：追踪与评估

日期：2026-09-10

## 一句话结论

没有 OpenAI 的云端追踪面板时，用三件事保证质量和成本可控：
本地日志负责“看清单次运行”，评估用例负责“重复衡量表现”，账单负责“控制花费”。

## 1. 本地日志代替 traces

所有脚本都设置了 `set_tracing_disabled(disabled=True)`，不向 OpenAI 发送追踪数据。
调试改看本地打印：

| 需要观察的内容 | 代码位置 | 日志示例 |
| --- | --- | --- |
| 模型是否调用工具、参数是什么 | `02_agent_with_tool.py` | `[工具被调用] find_student_home(name=cain)` |
| 工具返回了什么 | `02_agent_with_tool.py` | 最终回答中出现 `bible` |
| 哪个 Agent 接管了回答 | `04_multi_agent_handoff.py` | `实际回答的 Agent： history_teacher` |
| 敏感操作是否暂停、审批结果 | `06_human_approval.py` | `运行已暂停，等待人工审批` |

判断规则：日志里没有 `[工具被调用]`，说明这次模型没有调用工具（除非指令强制要求调用）。

## 2. 评估用例

脚本：`07_evaluate_agents.py`

核心结构：

```python
CASES = [
    {
        "name": "第3周：文件工具读取",
        "script": "02_agent_with_tool.py",
        "expected": ["工具被调用", "find_student_home", "cain", "bible"],
    },
    ...
]
```

`check_output()` 做的是“关键信息是否出现”的字符串检查：

```python
lowered = output.casefold()
return [word for word in expected if word.casefold() not in lowered]
```

返回空列表 = PASS；返回缺失词 = FAIL。

实验结果：

- 原始用例：3/3 通过；
- 把第一条的 `bible` 故意改成 `beijing`：输出 `FAIL`、`缺少期望内容：beijing`、通过率 2/3；
- 改回 `bible` 后恢复 3/3。

局限：只能检查关键词在不在，不能判断推理过程好不好；优点是不用额外模型、便宜、可重复。

## 4. 官方评估文档要点

原文：https://developers.openai.com/api/docs/guides/agent-evals

1. 调试阶段先用 traces 看单次运行的每一步（本项目用本地日志代替）；
2. 确定“好答案”标准后，把它固化成数据集和 eval run 做重复评估；
3. 比较提示词或模型版本时，看同一批用例通过率的变化。

## 我的复盘

- 日志和评估的区别：日志看一次运行有没有出错；评估用固定用例多次运行看整体通过率。
- 成本控制的关键：默认用 `deepseek-v4-flash`；不要让多轮 history 无限增长；每次实验后看账单。
