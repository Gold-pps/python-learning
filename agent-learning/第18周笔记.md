# 第 18 周笔记：混合检索 + 重排

日期：2026-09-28

## 一句话结论

本周把"只会比关键词"的检索换成了 **BM25 稀疏 + 向量稠密 + RRF 融合**，并给重排加上了
触发条件、失败降级与记账。最值钱的不是召回率涨了多少，而是三条**用数据推翻直觉**的发现：

1. **"两路都召回"在 RRF 里压倒一切**——哪怕它在两路里都排第 20 名，也能压过"单路第 1 名"；
2. **"相邻分数差 < gap 才触发重排"这个设计在 RRF 上失效**——因为 RRF 的分会**恰好相等**
   （`1/62+1/63 == 1/63+1/62`），最小分差恒为 0，任何阈值都触发；
3. **我的评测判据第一版就是错的**——只允许一个"正确答案文件"，把台账/进度里的同一条结论
   判成了错。改判据后混合检索从"和 BM25 打平"变成"来源命中 7/8 vs 5/8"。
   （又一次验证第 14 周的教训：**判据改了就必须重跑，否则分数没有意义**。）

> 逐条的"现象 → 根因 → 改法 → 验证"记在 `工程化改造记录.md`（本阶段台账）T20~T24，
> 本笔记只留结论、数字和教训。

## 2. 关键设计

### 2.1 RRF 按"排名"融合，不按"分数"融合

`score(d) = Σ_channels 1/(k + rank(d))`，k=60，rank 从 1 起算。

为什么不能用分数：BM25 的分数**没有上界、还可能为负**（rank_bm25 会把负 idf 批量替换成
`eps × 平均 idf`），余弦落在 [-1, 1]。归一化只能解决"范围"，解决不了"可比性"。

**用排名融合的代价，本周实测到了**：只要一个片段同时出现在两路候选里，
它就至少拿 `2/(60+20) = 0.025`，而"单路第 1 名"只有 `1/61 = 0.016`。
也就是说 **RRF 强烈偏好"两路都召回"，几乎无视名次**。
好处是稳健（不怕某一路胡说），坏处是**某一路只要稍微偏一点，就会把另一路的准确结果挤下去**
（本周末尾的 W18-7 就是：纯向量第 1 名是对的，混合反而掉出前五）。

### 2.2 "命中"的判定不能用分数，要用倒排表

`sparse_ranking()` 里判"哪些片段含查询词"，第一版写的是"BM25 分数不为 0"。
**这是错的**：rank_bm25 的 `BM25Okapi` 会把负 idf 替换成 `eps = epsilon × 平均 idf`，
当平均 idf 恰好是 0 时（例：2 篇文档、查询词只出现在 1 篇里）eps 也是 0，
于是**"词确实命中、分数却是 0"**。按分数过滤会把真命中静默丢掉。
现在改成构建 BM25 时顺手建一张 `token → 行号集合` 的倒排表，命中判定只看它。
（这个 bug 是写单元测试时撞出来的，不是读代码读出来的——见 T21。）

### 2.3 重排：三个显式分支

```text
候选 < 2 条        → 不触发
相邻最小分差 ≥ gap → 不触发（融合结果本身有把握）
相邻最小分差 < gap → 调 deepseek-flash，要求 {"ranking": [3,1,8]}
    解析失败/越界/调用异常 → degraded=True，退回 RRF 顺序（检索主链路不受影响）
```

- **严格 JSON**：只认 `{"ranking": [...]}`，元素必须是范围内整数（`bool` 不算）。
  唯一容忍的包装是 ``` 代码围栏。**不做"猜 JSON"式的修补**——那会把"模型没听懂"
  伪装成"重排成功"。重复编号按首次出现去重；未点名的候选按原顺序跟在后面。
- **降级是显式分支**：`RerankResult.degraded` + `reason` 一并返回，调用方一眼能看出
  "这次答案没重排过"。调用成功但 JSON 不合法时，**usage 照样记账**（钱花了）。
- **记账**：`usage = {prompt_tokens, completion_tokens, cached_tokens}`，
  CLI 会打印 `[重排用量]`。定价不进代码（价格会变），只记 token。
- **提示词前缀稳定**：固定指令放最前、问题与候选放最后，让 Context Caching 命中
  （第 7 周那条"缓存命中价约为未命中的 1/50"）。

### 3.1 抽查集对比（离线，不花 token）

| --------------------------------- | ---------- | ---- | ------ | --------- |
| 严格（来源文件对 **且** 片段含关键词） | 1/8 | 4/8 | 3/8 | **4/8** |
| 宽松（只看来源文件对不对）        | 1/8        | 5/8  | 6/8    | **7/8**   |

**必须诚实说清两件事**：

1. **严格判据下混合检索没赢 BM25**（都是 4/8）。差别恰恰出在判据上：我第一版只允许一个
   "正确答案文件"，而本项目的同一条结论同时写在周笔记、台账、学习进度里——
   把台账里的正确段落判成了错。加了"宽松判据"作为对照后，混合检索 7/8 明显领先。
   **两个数字都要报**，只报高的那个就是自欺欺人。
2. **关键词基线在自然语言提问上几乎必然 0 命中**，因为它要求"问题原样出现在片段里"。
   所以"基线没命中、混合命中"这种例子**赢得很廉价**，不能拿来证明混合检索好。
   真正有信息量的是 BM25 vs 纯向量 vs 混合这一行。

「文件对了、片段不对」有 3 条（W18-2 / W18-6 / W18-7）：检索找到了正确的文件，
但前五条没落在答案那一段。**这类问题要调切分粒度或 top_k，不是召回问题**——
第 19 周做对比表时要按这个分类去查因。

### 3.3 `RERANK_GAP` 校准：这个触发条件在 RRF 上失效了

拿每题混合检索的候选池（top20）算相邻分差，两个视角：

| 视角 | 各题最小分差 | gap=0.01 | gap=0.002 | gap=0.001 | gap=0.0005 |
| ---- | ------------ | -------- | --------- | --------- | ---------- |
| A：池内**任意**相邻对 | 全部 **0.00000** | 8/8 | 8/8 | 8/8 | 8/8 |
| B：**切分点**（第 5 名与第 6 名） | 0.00026 ~ 0.00996 | 8/8 | 7/8 | 5/8 | 4/8 |

**A 视角退化的原因**：RRF 的分是一组离散值，两路互相补偿时不同片段会**恰好相等**
（`1/62+1/63 == 1/63+1/62`），所以"最小相邻分差"恒为 0。照规划里的字面定义
（`相邻候选的 RRF 分数差 < RERANK_GAP`），**任何 gap 都触发，成本控制等于没有**。

**建议（留给第 19 周用数据决定，本周先只测不改）**：把"接近"的判定移到**切分点**上——
只有"第 top_k 名和第 top_k+1 名分不开"才值得重排。第 15、16 名黏在一起，对"取前 5 条"
毫无影响。B 视角下 `gap≈0.001` 能把触发率压到 5/8，且恰好是那些"边界真模糊"的题。

### 3.5 真实重排首跑（2026-09-28）：失败了，但失败得很有信息量

命令：`-m rag.rerank --query "为什么小批量向量化时不用 GPU？"`（你自己终端跑的 1 次调用）

| 项                       | 数值                                                      |
| ------------------------ | --------------------------------------------------------- |
| `triggered` / `degraded` | `True` / **`True`**（原因：回复不是合法 json）             |
| `prompt_tokens`          | 3,946                                                     |
| `completion_tokens`      | **256 = 我设的 `max_tokens` 上限** → 回复在 JSON 中途被截断 |
| `cached_tokens`          | 3,712 / 3,946 = **94%**（固定指令放最前面确实吃到缓存）    |

**两个结论，都已写进台账**：

1. **失败的直接原因是 `max_tokens=256` 太小**（T26）。截断 = 这次调用 100% 白花钱；
   更要紧的是：**降级原因没区分"被截断"和"模型乱答"，也没回显回复原文**——
   于是 FAIL 之后只能靠重跑才知道发生了什么（第 14 周 T10 的老毛病第二次犯）。
   已修：上限 → 1024；提示词要求"不要思考过程、最多列 5 个编号"；
   `finish_reason` 进 usage；降级原因回显回复开头 120 字。**复跑已验证（见 3.6）。**
2. **顺带暴露了检索本身的问题**（T27），证据离线可复现（不花钱）：

| 排序 | 片段                                                   | 融合分  | dense# | sparse# | 命中的查询词   |
| ---- | ------------------------------------------------------ | ------- | ------ | ------- | -------------- |
| 1    | `第16周笔记.md > 6. 我的复盘`（"留给你填"的空白小节）   | 0.03175 | 4      | 2       | 为什么、向、量化 |
| 4    | `第17周笔记.md > 2.4 双后端`（**真正的答案**）          | 0.01639 | 没召回 | 1       | 小批量、gpu     |

   两层机制叠在一起：

   - **分词把"向量化"切成了"向" + "量化"**（jieba 默认词典里没有"向量化"），
     "向"这种单字到处都是 → 那个空白小节靠 3 个**常见**词拿到稀疏第 2 名；
   - **RRF 只看名次、不看"命中得多好"** → 命中 3 个常见词的垃圾片段（0.03175）
     压过命中 2 个精确词（小批量 / gpu）的答案段（0.01639）。

   这也说明**重排在当前排序下是必要的**——它的活正是收拾这种排序；
   而这次重排恰好失败，你看到的就是"没被重排过、首条还是垃圾"的结果。
   第 19 周的候选改法（按性价比）：停用词/单字过滤 → 加权 RRF → jieba 用户词典。

### 3.6 复跑成功：重排真的把答案提上来了（同时又暴露一处逻辑矛盾）

第二次调用（修完 `max_tokens` 之后）：

| 项                             | 首跑（失败）                        | 复跑（成功）                          |
| ------------------------------ | ----------------------------------- | ------------------------------------- |
| `triggered` / `degraded`       | True / **True**                     | True / **False**                      |
| `finish_reason`                | （撞上限，`completion_tokens=256`） | `stop`                                |
| `prompt` / `completion` tokens | 3,946 / 256                         | 3,964 / 351                           |
| `cached_tokens`                | 3,712（94%）                        | **0**（我改了提示词 → 前缀全失效）     |
| 原因                           | 回复不是合法 json                   | 模型重排了 4 条                       |

**同一条查询，重排前后对比**：

| 位置 | 重排前（RRF）                                    | 重排后（LLM）                                        |
| ---- | ------------------------------------------------ | ---------------------------------------------------- |
| 1    | `第16周笔记 > 6. 我的复盘`（空白小节，0.03175）   | **`第17周笔记 > 2.4 双后端`（正确答案）**             |
| 2    | `第二阶段学习规划 > 2.2 选型表`                   | `学习进度 > 当前开发环境`                             |
| 3    | `第17周笔记 > 1. 本周做了什么`                    | `工程化改造记录 > T19 双后端实测`                     |
| 4    | **`第17周笔记 > 2.4 双后端`（正确答案）**         | `第17周笔记`（首节）                                  |
| 5    | `第11周笔记 > 6. 意外收获`                        | `第16周笔记 > 6. 我的复盘`（模型判为不相关，被代码补了回来） |

三条结论：

1. **重排确实有用**：答案从第 4 提到第 1，垃圾片段从第 1 掉到第 5。
   这是"混合 + 重排"相对"混合"的**第一份正面证据**（n=1，第 19 周要量出来）。
2. **模型挑得准**：点中的 4 条里，2 条是第 17 周正文、1 条是台账 T19（同一结论的另一处记录）、
   1 条是学习进度的环境小节。注意其中 `2.4 双后端` 那条**稠密侧根本没召回**（dense#None），
   是稀疏侧捡回来的——重排把两路的价值真正合到了一起。
3. **第 5 条暴露了我自己的逻辑矛盾**（详见 T28）：模型回复里**没有**那个垃圾片段，
   说明它被排除了；是我的代码"未点名的按原顺序补回去"又把它塞回最终结果。
   已修（只返回模型点过名的），顺带修了另一处更隐蔽的：`{"ranking": []}`（"都不相关"）
   被 `if not order` 误判成解析失败——而那正是第 19 周**无答案题**要用的信号。

## 4. 踩坑

1. **同一天里，两个第三方库的缓存都落进了仓库**：jieba 的词典缓存 9.25 MB 落在仓库根，
   fastembed 的 ONNX 模型 **90.8 MB** 落在 `notes-qa/fastembed_cache/`（还不在 `.gitignore` 里，
   一次 `git add -A` 就会把它提交上去）。根因是同一个：**它们的缓存目录默认走
   `tempfile.gettempdir()`，而 Windows 上环境变量取不到时它会静默回退到当前工作目录**——
   所以"挪到临时目录"这种修法**等于原地不动**（我第一版就是这么修的，实测无效）。
   现在两个缓存都显式指到 `data/` 下（`data/jieba.cache` / `data/fastembed_cache`），各配一条回归测试。
   （顺带发现：本环境下 pytest 的 `tmp_path` 也落在仓库里，同一根因，见台账 T20。）
2. **`rank_bm25` 里"分数为 0"不等于"没命中"**（eps 可能是 0）。见 2.2 / T21。
3. **控制台编码两连击**：Windows 控制台默认 GBK，
   ① 报告里写 `✓` / `✗` 直接 `UnicodeEncodeError`；
   ② 笔记正文里本来就有 ✅ 这类字符，`format_hits` 一打印就崩。
   修法：报告只用 ASCII 标记；CLI 里 `sys.stdout.reconfigure(errors="replace")`。
   **同一个坑一天踩两次**，所以第二次直接写成了通用函数 `make_stdout_forgiving()`。
4. **`index build` 的 `--backend` 从来没接上 `fastembed`**（`embedder.py` 支持，CLI 的 choices 里没有）。
   顺手补上，并加了一条守卫：**后端变了就不再算"增量"**，否则会把 bge 的旧向量搬过来、
   同时把 `meta.json` 的 model 改成 fastembed——数据没变、标签变了（T22）。
5. **判据第一版就是错的**（见 3.1）。这条最值得记：判据写错时，
   分数看起来完全正常，而且"混合检索不如 BM25"这种结论也说得通、很容易被接受。
6. **并行跑两个 `.venv-rag` 的解释器会互相打架**（一个报 "did not find executable"），
   串行跑就正常。以后冒烟测试别并发调同一个 venv。
