## 二、H2：补资料一条命令（四步，每步都有中断规则）

`uv run python -m rag.refresh`：预检 → 全量重建 → 检索冒烟 → 报"哪几处文档数字过期了"。

**真跑一遍（66 篇 / 3724 片段）**：

| 步 | 实测 |
| -- | ---- |
| 预检 | 文件 66、片段 3724、**失败 0**、空文档 0 |
| 建库 | 全量重算 3724 片段、退出码 0 |
| 冒烟 | 7 题 **33/35**（NC 类 5/5）——**与补资料后完全一致**，重建是确定性的 |
| 待改文档 | **3 处**（历史叙述残留） |

**踩到的坑，而且是熟病**：第 4 步第一版在真实语料上报了 **58 处**——历史记录里的
"44 篇入库""2501 片段"全被列出，**等于没筛**。这就是 T52 的同一个病（"命中率太高的判据就是噪声"）
**第二次发作**，所以记了 **T58**。加两道闸（只认"描述现状"的写法 + 含"历史/第 N 周/补前"的行整行跳过）
后降到 3 处；粒度是**按行**的，边界写进了测试断言。

## 三、H3：**我把这一项改了主意**（本阶段最该记的一次判断修正）

原计划：**开机自启 + 索引备份**。动手前重新问了一遍"这值不值得做"，两处都错了：

### ① 自启：收益抵不上风险

常驻监听（绑 `0.0.0.0` 就可能被同网段试口令）、"自动拉起的那个"与"我刚改完重启的那个"分不清、
排障多一层判断；而这个项目一个多月只用过 **37 次**——**手动三行命令的代价远小于常驻风险**。
**砍掉**，改成把"手动三步启动"写进 README 首屏。

### ② 备份对象搞反了

`data/index` 是**派生物**：66 篇重建一次 3724 片段、约 3 分钟（`rag.refresh` 干的就是这个）。
而 **`data/corpus/` 那 66 篇 PDF 既不在 Git（`data/` 在 `.gitignore`）、也没有任何备份**——
**那才是唯一不可替代的资产**。

### 改成了什么

`rag/backup.py`：`--check`（三方对账：语料 / 索引 / README）+ `--backup`（打 zip）。
**恢复演练真做过**：159.5 MB zip → 解压到独立目录 → 恢复 **66 篇 = 原始 66 篇**，子目录结构保留 ✓。

> 这条记的是**顺序**：先问"这件事解决什么问题"，再问"怎么做"。
> 我原来的写法是"因为要显得完整，所以加自启"——那正是这个仓库一直在防的东西。

## 六、三条规律（这一阶段真正学到的）

1. **文档里的数字，要么给命令、要么带口径**。写过三次的东西不该第四次靠人记得改——
   T56 的解法不是"下次注意"，是**守卫测试**（裸累加值禁写 + 语料规模对账）。
2. **命中率太高的判据就是噪声**（T52 → T58 第二次发作）。
   "42/46 全被标""58 处待改"跟"一条不报"一样没用；判据的价值在**能把范围缩到看得完**。
3. **先问"值不值得做"，再问"怎么做"**。自启与备份对象这两处，都是计划阶段就想错、
   动手前问一句才发现——**计划里的"完整性"最容易变成无用功**。
