# 第 6 周笔记：安全与护栏

日期：2026-09-08

## 一句话结论

护栏（guardrail）负责“自动检查”，人工审批（human review）负责“需要人拍板的敏感操作”。
前者用代码或模型自动拦截，后者让运行暂停，等人批准或拒绝后再继续同一轮任务。

## 三种护栏放在哪里

| 类型 | 检查时机 | 适合做什么 |
| --- | --- | --- |
| 输入护栏 input guardrail | 模型开始处理前 | 拦截明显违规或危险的用户请求 |
| 输出护栏 output guardrail | 最终回答返回前 | 检查、拦截或脱敏敏感内容 |
| 工具护栏 tool guardrail | 工具调用前后 | 检查工具参数和工具返回结果 |

注意两个边界：

- 输入护栏只在链路里的第一个 Agent 上运行；
- 输出护栏只在最终产出回答的 Agent 上运行。

## 实验一：输入护栏与输出护栏

运行：

```bash
python 05_guardrails.py
```

验证结果：

```text
=== 演示 1：输入护栏 ===
输入护栏已拦截请求，模型没有开始处理。
触发条件：输入中包含危险操作关键词。

=== 演示 2：输出护栏 ===
输出护栏已拦截回答，疑似密钥没有返回给用户。
触发条件：回答中匹配到 sk- 开头的疑似密钥。
```

关键代码：

```python
@input_guardrail(name="block_dangerous_operations", run_in_parallel=False)
def block_dangerous_operations(ctx, agent, user_input):
    ...
    return GuardrailFunctionOutput(
        output_info={"matched_patterns": matched},
        tripwire_triggered=bool(matched),
    )
```

`run_in_parallel=False` 表示护栏先于主 Agent 运行；如果 `tripwire_triggered=True`，
SDK 会抛出 `InputGuardrailTripwireTriggered`，主 Agent 不会继续执行。

## 实验二：敏感操作人工审批

运行：

```bash
python 06_human_approval.py              # 运行时询问 y/N
python 06_human_approval.py --decision approve
python 06_human_approval.py --decision reject
```

审批生命周期：

1. 模型决定调用 `delete_file`；
2. SDK 发现这个工具设置了 `needs_approval=True`，于是暂停运行；
3. `result.interruptions` 里出现待审批的 `ToolApprovalItem`；
4. 用 `result.to_state()` 拿到可恢复状态；
5. 调用 `state.approve(item)` 或 `state.reject(item)`；
6. 再执行 `Runner.run(agent, state)`，从暂停处继续。

验证结果（拒绝）：

```text
运行已暂停，等待人工审批：
- 工具：delete_file
  参数：{"path": "agent学习/临时文件.txt"}

审批结果： 拒绝
最终回答： 删除操作已被拒绝，因此 agent学习/临时文件.txt 未被删除。
```

验证结果（批准）：

```text
[工具已执行] delete_file(path=agent学习/临时文件.txt)

审批结果： 批准
最终回答： 文件 agent学习/临时文件.txt 已成功删除。
```

## 我的复盘（待你运行后填写）

- 我观察到输入护栏和输出护栏分别在什么时刻生效：
  输入护栏在模型开始处理前生效：`Runner` 收到用户输入后先执行输入护栏，
  一旦命中危险关键词就抛出 `InputGuardrailTripwireTriggered`，主 Agent 不会被调用。
  输出护栏在 Agent 生成最终回答之后、回答返回给用户之前生效：模型已经完成生成，
  护栏检查到敏感内容后抛出 `OutputGuardrailTripwireTriggered`，阻止这段回答返回给用户。
- 我发现“拒绝”和“批准”后，模型回答有什么不同：
  拒绝后：审批中的工具没有被执行，SDK 把“用户拒绝”告诉模型后继续，
  模型会基于“操作未执行”生成回答，例如“删除操作已被拒绝，文件未被删除”。
  批准后：SDK 放行这次工具调用，工具函数真正运行并返回结果，
  模型再基于执行结果生成确认性回答，例如“文件已成功删除”。
  注意：06 的 `delete_file` 是演示工具，批准后也只是打印提示，并不会真的删除文件。
- 如果要把审批接到真实删除文件、发送邮件或下单操作上，我会怎么改：
  整体思路对：审批流程不用改，保留 `needs_approval=True`，
  把 `delete_file` 的函数体替换成真实实现（或按业务新建不同工具）即可。
  但真实操作还需要注意三点：
  1. 参数与校验：定义完整参数（路径、收件人/主题/正文、订单号等），
     并在函数里校验，防止删错路径、发错对象或金额异常；
  2. 安全与幂等：删除前确认路径在允许范围内，最好先进回收站；
     发邮件、下单要考虑重复点击造成重复执行，可加幂等键；
  3. 结果与错误：让真实工具返回明确的成功/失败结果或抛出异常，
     模型才能基于真实结果组织最终回答，而不是编造“已删除/已发送”。
