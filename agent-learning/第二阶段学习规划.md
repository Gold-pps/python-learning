### 关键术语速查（本阶段新出现的词，读到不懂时回来查）

| 术语                | 一句话解释                                                                |
| ------------------- | ------------------------------------------------------------------------- |
| chunk（片段）       | 长文档切成的可检索小块，本阶段目标 300~500 字/片、重叠 50 字              |
| embedding（向量化） | 把文本变成一串数字，语义相近的文本向量距离近                              |
| 稠密检索            | 用 embedding 向量算相似度找片段（能找"意思相近但用词不同"）               |
| 稀疏检索 / BM25     | 基于词频的传统检索（找"用词相同"），本项目用 `jieba` 分词 + `rank_bm25`   |
| 混合检索            | 同时跑稠密 + 稀疏，再把两路结果融合                                       |
| RRF                 | Reciprocal Rank Fusion，按"排名"而不是"分数"融合两路结果，避免量纲不一致  |
| rerank（重排）      | 对初筛出的候选再排一次序，本阶段用 `deepseek-flash` 把前 20 名压到前 5 名 |
| 多跳检索            | 一次检索不够，先查一轮 → 看出缺什么 → 再查一轮（本阶段上限 2 轮）         |
| Recall@5            | 前 5 条结果里是否包含正确答案所在片段的比率                               |
| 引用准确率          | 答案里标注的来源，是否真的支持该结论                                      |
| 无答案拒答率        | 资料里确实没有答案时，模型正确回答"资料中没有"的比率                      |
| cp314 轮子          | 预编译好的安装包，带 `cp314` 标记表示支持 Python 3.14；没有就得自己编译   |

## 一、阶段定位与四个目标

## 二、技术路线与选型（含环境约束）

### 2.1 三个已核实的前提，决定了选型

| 前提                                 | 核实结果                                                                       | 对设计的影响                                                                            |
| ------------------------------------ | ------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------- |
| DeepSeek 是否提供 embedding / rerank | **都没有**（官方文档导航与 API 页面均无相关接口）                              | 向量化与重排**必须本地实现**；重排可选"本地分数融合"或"用 `deepseek-flash` 做 LLM 重排" |
| DeepSeek Files API 能否当文档库      | **不能**：仅支持图片（JPEG/PNG/GIF/WebP），不支持 PDF/Word/txt，且不做任何检索 | PDF/Word/txt 必须**本地解析**后再入库                                                   |
| 本机算力                             | 纯 CPU、8 核、内存 7.2 GB（当前可用约 2.3 GB）、无 CUDA                        | 模型要小、批处理要可控、索引要落盘复用，**不引入重型向量库**                            |

### 2.2 选型表（全部经过可用性实测）

| 需求          | 选定方案                                                   | 实测依据                                                                                                                                                                  | 备选 / 排除                                                                                                     |
| ------------- | ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| 对话模型      | `deepseek-flash`（延续）                                   | 已有 `.env` 与三段配置                                                                                                                                                    | `deepseek-v4-pro`（现按 Flash 计费，无必要）                                                                    |
| 本地向量化    | `sentence-transformers 6.0.1` + `BGE-small-zh-v1.5`        | torch 2.14.0 有 **cp314 轮子**；sentence-transformers 是纯 Python 包                                                                                                      | `fastembed` + `onnxruntime 1.30.0`（也有 cp314 轮子）作为省内存备选                                             |
| 向量检索      | **不用向量库**，`numpy` 暴力余弦 + 落盘缓存                | 规模估算：一篇论文约 10~25 片（按 300~500 字/片），30 篇 ≈ 300~750 片、300 篇 ≈ 3000~7500 片；**5 万片以内暴力检索都是毫秒级**，占内存约 100 MB（50000 × 512 维 float32） | ❌ `faiss-cpu 1.15.0` 无 cp314 轮子；❌ `chromadb` 最新版无通用轮子。**仅当片段数 >5 万或内存放不下**时才重新评估 |
| 稀疏检索      | `jieba`（中文分词）+ `rank-bm25`                           | 两者都是纯 Python 轮子                                                                                                                                                    | SQLite FTS5（无依赖，但中文分词需自己接）                                                                       |
| 文档解析      | `pypdf`（PDF）+ `python-docx`（Word）+ 内置（md/txt）      | 两者均有纯 Python 轮子                                                                                                                                                    | 图片型 PDF 走 Vision 识图——**不是**传统 OCR 工具（如 tesseract），见下一行与第五节风险表                        |
| 扫描件 / 图片 | `deepseek-flash` 的 **Vision** 能力                        | 官方文档已核实：支持截图读文字；base64 / URL / `file_id` 三种输入                                                                                                         | 同一张图反复用 → Files API 的 `file_id`（单图上限 32 MiB → 64 MiB）                                             |
| 重排          | 先用 **RRF 分数融合**，再视效果加 LLM 重排（top20 → top5） | 无 rerank 接口，只能自己实现                                                                                                                                              | 本地 cross-encoder（内存吃紧，暂缓）                                                                            |
| Web 界面      | `FastAPI` + `uvicorn` + 原生 HTML/JS                       | 均有纯 Python 轮子                                                                                                                                                        | Gradio（更省事，但定制性差）                                                                                    |
| 工程化        | `pyproject.toml` + `uv.lock` + `pytest` + `ruff`           | uv 0.12.10 已具备                                                                                                                                                         | `mypy`（可选，先保证测试覆盖，不强推）                                                                          |

### 2.3 内存策略（本机只有 2.3 GB 可用，必须当回事）

1. **embedding 一次性批处理并落盘**：`data/index/` 下存 `vectors.npz` + `chunks.jsonl`，
   日常查询只读缓存，不重复加载模型；
2. **用独立虚拟环境**：`notes-qa` 主环境保持轻量，向量化相关依赖单独放 `.venv-rag`，
   跑完索引就退出，避免 torch 常驻；
3. **限制线程数**：`torch.set_num_threads(4)`，批大小 8~16，宁可慢也别 OOM；
4. **模型只选 small 级**：`BGE-small-zh-v1.5`（约 95 MB、512 维），不碰 `large` / `bge-m3`；
5. **中英混合的处理**：中文片段用中文模型；英文片段先靠 BM25，若召回不足再引入
   `bge-small-en-v1.5`（两个模型**分两次索引**，不同时驻留内存）；
6. **降级预案**：内存不足时切 `fastembed`（onnxruntime）或退化为纯 BM25 + LLM 重排，
   功能不减、只损召回率——这是**显式分支**，不是口头兜底。

### 2.4 顺带能用上的 DeepSeek 能力（不额外花钱）

- **Context Caching**：指令前缀稳定就能命中缓存（第一阶段已验证缓存命中价约为未命中的 1/50），
  新项目的 system prompt 要保持稳定；
- **JSON Output**：结构化摘要（研究现状 / 方法 / 结论 / 可复用点）用 JSON 模式，省掉脆弱的后处理解析；
- **Thinking Mode**：只在"综述型问题"上开。判据**可执行化**——问题里出现"有哪些方法 / 对比 / 现状 /
  趋势 / 优缺点"这类词，或用户显式加 `/deep` 前缀时才启用，其余一律不开（第 21 周按此实现）；
- **Responses API / Anthropic 兼容端点**：主流框架可直接接，属于"知道有这条路"即可。

## 四、每周执行建议

- **节奏**：周中 3 次各 40 分钟（读文档 / 写代码）+ 周末 1 次 2.5 小时（整块攻坚 + 写笔记）；
- **每周一个可运行产出**：延续第一阶段最成功的设计——没有产出的那一周，等于没学；
- **每周一篇笔记**：命名接续第一阶段，从 `第13周笔记.md` 开始，格式沿用
  "一句话结论 / 关键实现 / 实测记录 / 踩坑 / 我的复盘"；
- **重活放低谷时段**：批量建索引、跑评测这类耗 token 的实验放在工作日 18:00 后或周末
  （低谷价是高峰价的一半），高峰期只做一次性小验证；
- **每次实验后打印 usage 并记进笔记**，每周核对一次账单，格式沿用 `第7周笔记.md` 的成本表；
- **每周顺手做一次"AI 审查"**：第 11 周证明这个模式能找到人肉 review 漏掉的真 bug，
  第二阶段的改动量更大，建议固化成习惯；
- **卡住时的顺序**：先看官方文档 → 再问 AI → 最后搜博客；涉及破坏性操作（如历史重写）**先备份**；
- **单周超载时的裁剪顺序**：先砍"验证性任务"（例如多跑几组参数对比），再砍"优化性任务"（调参），
  **绝不砍"产出与评测"**——这两样是本阶段不可压缩的部分；

## 五、风险与备选方案

| 风险                           | 触发信号                                      | 应对方案                                                                                                                                                                                                     |
| ------------------------------ | --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 内存不足导致 embedding OOM     | 建索引时被系统 kill / 可用内存 <500 MB        | 切 `fastembed`（onnxruntime）→ 仍不行则退化为纯 BM25 + LLM 重排（第 17 周已把这两个分支做成开关，直接切即可）                                                                                                |

| 扫描版（图片型）PDF 解析为空   | `pypdf` 提取出的文本长度为 0                  | 走 Vision 支线：PDF 转图片 → `deepseek-flash` 识字（只对关键文档做，控制成本）                                                                                                                               |
