## 2. 目标与约束

### 2.1 老师方案的要点（我的理解）

主链路：

> 3D 模型解析 → 补制造条件 → **候选工艺方案** → NX CAM 任务配置 → 刀轨计算 → 后处理
> → **候选 NC 程序** → 静态检查 → 专业仿真 → 人工审核 → 反馈修订

关键定位（方案原文的口径）：

- 大模型的活：**知识整理、输入完整性检查、相似案例检索、候选工艺解释、任务编排、状态跟踪、错误辅助诊断**；
- 大模型**不做**：专业 CAM 计算、后处理、碰撞/过切修复、人工审核替代；
- 一期只做**仿真验证闭环**，不含真机加工；
- 有**任务编号**（如 `TURN-2026-0001`）和**十个状态**（待解析 → … → 仿真完成 / 执行异常）。

### 2.2 我的约束（请务必按这个来设计任务）

| 约束 | 说明 |
| --- | --- |
| **没有 NX / CAM 许可证** | 任何需要真工业软件的环节，只能做**接口骨架 + 契约测试 + 假节点** |
| **预算** | 单次实验 ≤ **0.1 元**；能不花钱就不花钱（模型调用按 2~7 分/次算） |
| **时间** | 每周 3~5 小时；**每个阶段要能一周内出成果** |
| **展示** | 必须能在组会上一页讲清、有可演示的东西（新内容优先） |
| **环境** | Windows + PowerShell；离线优先；不引入需要许可证的组件 |

## 2.5 代码放哪里、四条硬规矩（2026-10-27 定）

**结论：同仓库、新建一个并列目录 `agent-learning/process-ai/`。**
不塞进 `notes-qa/`，也不另开新仓库。

| 做法 | 问题 |
| --- | --- |
| 塞进 `notes-qa/` 里 | 概念不同（**资料问答** vs **工序链**），混在一起 `notes-qa` 会变成杂物间；它的测试已依赖 `fastembed` + `jieba`，再加一块只会更慢 |
| 另开一个新仓库 | `pyproject` / `uv.lock` / `ruff` / `pytest` 配置 / CI / 台账 / `.gitignore`（含已踩过的坑的注释）**全部要重搭**——这些坑已经踩过两次，没必要再来一次 |
| **同仓库、并列目录** ✅ | 复用全部工程骨架；CI 自动覆盖；展示时是"**一个平台两个能力**"，比"两个不相关小工具"好讲 |

目录结构（目标态）：

```
python-learning/
├─ pyproject.toml                 # 已有：testpaths 要加一条
├─ .github/workflows/ci.yml       # 已有：自动带上新测试
└─ agent-learning/
   ├─ notes-qa/                   # 已有：资料问答（**不动它**）
   └─ process-ai/                 # 新建：对齐实验室方案的工序链
      ├─ process_ai/
      │  ├─ nc_check.py           # 阶段 1：G 代码静态检查
      │  ├─ statemachine.py       # 阶段 2：任务状态机
      │  ├─ fake_cam.py           # 阶段 2：假 NX CAM 节点（超时/错误码/产物）
      │  └─ rules.py              # 阶段 3：结构化工艺规则
      ├─ samples/                 # 少量样例（坏 G 代码、小 STEP），几十 KB，可进 Git
      └─ tests/
```

命名推荐 **`process-ai`**（工艺智能）——准确覆盖"工艺编制 + NC 程序"两端，写进组会标题也自然。
备选：`mfg-lab`、`nc-lab`（后者太窄，状态机放进去就别扭）。

**四条硬规矩**（都是为了不再踩重复的坑）：

1. **不跨包 import**。唯一例外是 **MCP 薄壳**：`process_ai` 不许 import `notes-qa` 的任何东西；
   反过来 `notes-qa/mcp_server` 可以 import `process_ai`，把 `check_nc_program` 挂成第 4 个工具——
   这样是"**Agent 一个入口、两个能力**"，而不是两个孤岛；
2. **各有各的测试**。`process_ai/tests/` **不许依赖 `data/index`**——必须在"没有语料、没有索引"的机器上
   也能全绿（这条是 CI 红过两次换来的：`data/` 在 `.gitignore`，CI 上没有）；
3. **数据不共用**。`notes-qa/data/` 是 70 篇论文；`process_ai` 只需要少量**标准/规则样例**
   （G 代码片段、小 STEP 文件），放 `process_ai/samples/`，体积小到可以进 Git；
4. **第一天就把测试路径接进 CI**。新包一建好就要把 `agent-learning/process-ai/tests` 写进
   `pyproject.toml` 的 `testpaths`，否则 CI 永远不跑它——"写了测试但没接进 CI"和"没写"一样。

## 3. 学习路线（四个阶段，按"一周一个可交付"切）

> 排序原则：**先做"可离线、可评测、10 秒能看懂"的**，再往上长；
> 不按"知识体系完整性"排，按"**能不能在下一次组会上拿出来**"排。

### 阶段 1（第 1 周）：G 代码静态检查器 + 包成 MCP 工具

| 项 | 内容 |
| --- | --- |
| **为什么是这个** | 老师方案里明确要求"语法、模态状态、坐标范围、刀具补偿、圆弧参数、安全进退刀、程序完整性"检查；而它**纯 Python、离线、可评测**，还正好能接上我已有的 MCP 链路（展示时是"Agent 调工具做检查"，不是脚本） |
| **要补的知识** | G 代码基础（G0/G1/G2/G3、G90/G91 绝对相对、G54~G59 坐标系、M03/M05/M08、F/S 模态）、模态组概念、圆弧 I/J/R 参数一致性、程序结构（程序号/程序段/结束） |
| **最小可交付** | `rag/nc_check.py`：解析器（逐段 token 化 + 模态状态跟踪）+ **6~8 条规则**（未知 G 代码 / 圆弧参数不一致 / 坐标超行程 / 未定义模态 / T+刀具补偿未配对 / 无程序结束 / 进给为零 / 安全 Z 起点）→ 输出「行号 + 规则 + 依据 + 严重级」 |
| **验收判据（可核）** | ① 一组**故意写坏**的样例各自命中对应规则（pytest ≥8 条）；② 一段**正常**程序 0 误报；③ `check_nc_program` 作为 MCP 第 4 个工具能被 Codex 调用（截图/日志为证）；④ 开销 0 元（纯本地） |
| **展示点** | 现场贴一段 G 代码 → 10 秒内报出 3 类错误，并说明"这条规则来自哪篇论文/标准"（我语料里有 14 篇 NC 方向论文可引用） |

### 阶段 2（第 2 周）：任务状态机 + 工业软件节点骨架

| 项 | 内容 |
| --- | --- |
| **为什么** | 方案的核心不是"算得准"，是"**一条链跑得稳、可追溯**"；这是我最缺的工程能力（长流程编排） |
| **要补的知识** | 状态机建模（状态/事件/迁移/守卫）、幂等与重试、任务实体与产物关联、**契约测试**（接口签名/超时/错误码）、外部进程编排 |
| **最小可交付** | ① `任务` 实体（编号 `TURN-YYYY-NNNN` + 状态 + 产物路径）；② 状态机（**先做 4 个状态**：待解析 → 待生成 → 待检查 → 完成/异常）；③ 一个 `FakeCamNode`（模拟 NX CAM：有超时、有失败码、有产物文件）；④ 每个迁移写日志（谁触发、耗时、产物） |
| **验收判据** | ① 一次任务能从"待解析"走到"完成"，**每步都有日志与产物**；② **故意让节点超时一次**，系统重试 1 次后降级为"待人工"并留下原因；③ 同一任务重放不产生重复产物（幂等，有测试）；④ 契约测试覆盖"节点返回异常码/超时/产物缺失"三种失败 |
| **展示点** | 演示"注入一次失败"→ 系统如何重试/降级/留痕。**这比演示成功更有说服力** |

### 阶段 3（第 3~4 周）：结构化工艺规则库 + 混合检索

| 项 | 内容 |
| --- | --- |
| **为什么** | 方案用"规则库 / 模板库 / 案例库"三件套，而我现在只有**非结构化论文**；这是我能力结构的空白 |
| **要补的知识** | 结构化知识建模（表/YAML/JSON schema）、规则与证据分离、混合检索（结构化过滤 + 语义检索）、案例相似度 |
| **最小可交付** | ① 从论文里抽出 **20~30 条**工艺规则（如"粗车→精车余量""淬火后需磨削"），每条**必须带出处**（论文 + 页码）；② `rag/rules.py`：按零件特征/材料/机床**过滤**规则，再交给语义检索排序；③ 一次问答同时给"规则命中"和"论文证据"两条来源 |
| **验收判据** | ① 每条规则都能回查到原文（延续我已有的引用对账口径）；② 同一问题在"加规则"后**至少一条结论变得更具体**（有对照记录）；③ 规则库 0 幻觉：抽 5 条人工核，**不许有原文没有的规则** |
| **展示点** | 同一句提问，展示"规则命中（结构化）+ 论文证据（引用）"两条来源，说明**为什么要两条** |

### 阶段 4（可选，第 5 周起）：3D 回转体特征解析

| 项 | 内容 |
| --- | --- |
| **为什么** | 方案第一步是 3D 解析；做出来**视觉冲击最强**，但一周做不完、且与我的强项关系最弱 |
| **要补的知识** | STEP 文件结构、OpenCASCADE（`pythonocc`/`cadquery`）、回转体特征（端面/外圆/台阶/圆弧/锥面）判据 |
| **最小可交付** | 读一个 STEP → 输出"有哪些圆柱面/平面/锥面 + 尺寸"→ 映射成 5 条车削特征候选（人工确认） |
| **验收判据** | 3 个零件的特征清单与人工判断一致（允许漏 1 个，不许瞎报） |
| **展示点** | 3D 模型 → 特征表，一图胜千言 |
| **建议** | **只有前三阶段都做完、且组会还需要新东西时再做** |

## 4. 明确不建议学（附理由，避免教学 AI 带我走偏）

| 不做 | 理由 |
| --- | --- |

## 5. 现状与未决（防止教学 AI 误判我已会/已在做）

### 5.1 已停掉的线
- 检索覆盖调参：**四个旋钮都量过**，结论写在 `eval/检索覆盖-子主题先验实验.md`；
- 加权接生产：实测 **33/35 → 31/35**，已回退（台账 T57）。

### 5.2 唯一"有效但前提未满足"的发现
- **"补检命中时重置候选"** 能让方法覆盖从 1/7 到 **7/7**（17 条候选，且仍含 2 篇综述）；
- 但前提是**补检查询要具体到方法名**，而 `plan` 阶段**看不到"库里有哪些方法"** →
  给它加"必须给方法名"的提示词**实测无效**（补检触发 4 轮，仍是"振动监测/传感器"这类泛方向，0/7）。
- **要闭合它，需要把语料标题清单喂给 plan**（数据通路改动），我**没做**。

### 5.3 本质边界
- **引用可核 ≠ 结论正确**。目前 46 条结论：3 条逐条核对 + 43 条通读，支持 45 / 无法判断 1；
  17 条纯文字结论**机器完全核不了**。

## 6. 给教学 AI 的开场指令（复制这一段 + 上面全部内容）

```
你是我的技术教练。下面是一份交接文档，描述我已经做完的项目、我真实会的/不会的、
以及下一步要往"数控车削智能工艺编制 + 候选 NC 程序生成"靠的学习路线。

请按这个规矩带：

1. 一次只推进一个最小可交付（一周量级），不要给"完整学习计划"式的排比；
2. 每个任务必须给出**可核的验收判据**（能写成断言/能跑出数字的那种），
   不要"理解了""掌握了"这种没法验的说法；
3. 我环境受限：没有 NX/CAM 许可证，凡是需要工业软件的环节，教我怎么做
   **接口骨架 + 契约测试 + 假节点**，而不是让我去装软件；
4. 预算敏感：任何要调用大模型的任务，先说清大概花多少（我按 2~7 分/次算）；
5. 我有个习惯：**结论必须能回查**。如果你给我一个技术判断，请说明依据
   （文档/实测数据/你的推断，三者要分开标）；
6. 如果我的路线有问题（比如某阶段不划算、顺序该换），**直接说**，
   不要顺着我。我更希望被纠正一次，也不想按错的路走三周；
7. 新代码统一放 `agent-learning/process-ai/`（新包），**不塞进 `notes-qa/`**；
```
