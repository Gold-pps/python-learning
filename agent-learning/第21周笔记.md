# 第 21 周笔记：综述型问答（四段式 + 可回查引用）

日期：2026-10-09

## 一句话结论

本周把 Agent 从"回答某个事实"推进到**回答"这个方向有哪些方法、各自优缺点"**：
检索侧加了三道约束、回答侧做成"盘点 → 补检 → 组织"的**两调用流水线**，
产出四段式（研究现状 / 方法对比 / 结论 / 可复用点）JSON，每条结论挂 `[文件:位置]` 引用。

最值钱的是三件事：

1. **"要挂引用"写在提示词里只是请求，写进代码才是约束**：三题共 **55 条引用，0 编造**，
   而且失败时校验正确地"什么都不说"（0/0/0，没有假装有引用）；
2. **输出预算必须按"思考 + 答案"估，而答案长度由我们要求的结构决定**：
   首跑 3/3 被 4096 截断（1 题连答案都没开始写），提到 8192 后 3/3 全部 `stop`——
   **T30 那条教训第二次现形**，这次栽在"答案变长了"上；
3. **一次误操作（`--query "..."`）送了一份最好的负样本**：模型 4 段全空、明确说
   "资料中没有提供明确的用户问题"、0 编造——"无依据必须说资料中没有"在最极端的输入下也成立。

> 逐条的"现象 → 根因 → 改法 → 验证"记在 `工程化改造记录.md` T32~T34；
> 检索侧覆盖见 `eval/第21周检索冒烟.md`，三份真跑报告见 `eval/第21周综述问答-R21-*.md`。

## 2. 关键设计

### 2.1 架构：检索与 Agent 同进程（选 A）

三个候选想过一遍：

| 方案 | 做法 | 结论 |
| ---- | ---- | ---- |
| **A（采用）** | 主 `.venv` 加可选依赖组 `rag`（fastembed + ONNX，**不装 torch**） | 同进程、BM25 只建一次；代价只是主环境多约 100~200 MB |
| B | 检索留在 `.venv-rag`，子进程调用 | 每次工具调用都要重跑一次 2501 片段的 jieba 分词 + 建 BM25 |
| C | 把 `openai-agents` 装进 `.venv-rag` | 破坏 T18 的依赖隔离（`rag` 不该依赖 `agents`） |

`uv sync` 不受影响（CI 不跑检索），要检索时 `uv sync --extra rag`。

### 2.2 为什么是"两调用流水线"，而不是 Agent 工具循环

规划的产出写的是"更新 `agent.py` 指令"，**我没有那么做**，改成了代码驱动的流水线
（`rag/review_qa.py`），理由是：

- SDK 工具循环里"模型自己决定检索几轮"→ **成本不设上限**，与规划
  "多跳最多 2 轮、防成本失控"直接冲突；
- JSON Output 约束、引用对账、无依据声明都需要**代码级**控制；交给提示词只是请求。

实际形状（每题 **2 次模型调用**，检索不花钱）：

```text
① 混合检索（top_k=5，每篇上限 2，排除不可引用源）
② 调用 1「盘点」→ {"enough": bool, "gaps": [...], "follow_up_queries": [...]}
      ↑ 调用失败/解析不了 → 跳过 ③，直接进 ④（盘点失败不该丢掉答案）
③ 补检（只在"不够"且给了查询词时做，最多一轮、≤3 条查询）
④ 调用 2「组织」→ 四段式 JSON
⑤ 引用校验（拿候选集合对账）
```

**盘点的实际价值**（三题都判"有缺口"，补检后候选 5 → 10）：它的 `gaps` 写得相当具体，
例如"只覆盖数据驱动建模，缺少机理/物理建模与经验建模""缺少等参数线法、截面线法、
投影法等轨迹规划方法的系统分类"。这份"缺什么"清单本身就是下一步该补什么的线索。

### 2.3 引用校验：三档分开记，而不是一刀切

`validate_citations()` 拿**候选集合**去对模型给的每条引用：

| 档位 | 含义 | 处理 |
| ---- | ---- | ---- |
| 精确 | `文件:位置` 与某个候选完全一致 | 计入，可回查到页/段 |
| 缺定位 | 只写了文件名 | 计入，但标注"还没到页" |
| **编造** | 文件根本不在候选里 | **单独记账**（不静默删掉——删掉就看不见问题了） |

外加一个"无引用条目"计数：某条结论一条引用都没挂也照样报告，
因为"模型没给引用"是要报告的事实，不是要替它抹平的瑕疵（T28 的教训）。

`_canon()` 归一化只去方括号和空白：让"多一个空格"不算编造，但**绝不放宽到"按文件名猜"**。

### 2.4 检索侧三约束的来历与效果

| 约束 | 治什么 | 实测效果 |
| ---- | ------ | -------- |
| `max_per_source=2` | 一篇综述同时命中小节标题与正文，天然占满 top-5 | "不同论文数" 2~4 → **3~4 篇**（R21-4 从 2 → 4 最明显） |
| `subtopic` | "研究现状"这类词把相邻子主题的综述拉进来 | 覆盖表 24/25 命中期望子主题；**默认不开**，因为跨方向综述有时恰好最相关 |
| `exclude_unreadable` | 那 2 篇 `/G` 乱码论文能凭标题命中，却引用不出可读原文 | 排除 **23 条片段 = 抽查记录的 18 + 5**，分毫不差 |

第三条的意义：**"仅存在性可检索"如果只写在 `rag/解析质量抽查.md` 里，答题时没人执行**。
落到检索层之后，`with_bad` 那条复现路径（`exclude_unreadable=False`）也留着。

### 2.5 思考模式判据：关键词要取"半步"

判据是"问题里出现某些词，或显式 `/deep` 前缀"。第一版写的是 `"有哪些方法"`，
而真实提问是 **"有哪些主流方法"**——差一个"主流"就命不中（写测试时才发现）。
现在用"半步"关键词（`有哪些` / `哪些方法` / `对比` / `现状` / `趋势` / `优缺点` / `综述` / `进展`），
宁可多开一次思考，也不要漏判。

另外：**模型名由使用者给**（`--thinking-model`），不猜。真跑时三题判据全命中、
用的仍是默认模型——本项目的默认模型本身就会内部推理（见 3.1）。

## 3. 实测记录

### 3.1 首跑 3/3 全被截断：T30 的第二次现形

| 题 | `finish_reason` | completion | 现场 |
| -- | --------------- | ---------- | ---- |
| R21-1 | `length` | 4096（=上限） | 回了半个 JSON |
| R21-2 | `length` | 4096（=上限） | **回复为空**——思考把预算全吃光了 |
| R21-4 | `length` | 4096（=上限） | 回了半个 JSON |

定位只花了一次运行，因为报告里带着 `finish_reason` / usage / 回复开头
——**T26 那次修复在这里回本了**（第 18 周得跑第二遍才知道为什么 FAIL）。

修法三处：① 回答预算 **8192**；② 提示词加篇幅上限（每段 ≤4 条、`point` ≤60 字、
每条 ≤2 个引用，并明说"宁可少写几条，也别写到一半断掉"）；③ 降级原因补一句可执行处置
（"先让每段写短，再调大 `--max-tokens`"）。

**复跑 3/3 全部 `finish_reason=stop`，而且没有一次用满预算**——
说明 8192 是真余量，不是刚好够。

### 3.3 引用回查：抽查 4 条，4/4 逐字对得上

方法：直接从索引里取出被引用的 `(文件, 页)` 片段原文，与答案里的结论逐字比对（离线、不花 token）。

| 被查的结论 | 原文 | 结论 |
| ---------- | ---- | ---- |
| 直接法"离线、停机降效率" | "直接法都不适用于在线监测，同时测量过程的停机耗时降低了切削加工效率" | ✅ |
| 电流传感器"经济、便于安装，但灵敏度与抗干扰弱" | "电流传感器最大的优势是经济性强，便于安装，但灵敏度和抗干扰能力较弱" | ✅ |
| MAE 降低 20.3% / 25.9% / 44.6% | "EMMIDA 填补方法的 MAE 相比 MICE、GAIN 和 KNN 分别降低了 20.3%、25.9%、44.6%" | ✅ |
| 插补误差 1.5 μm → 0.37 μm | "CHEN 等[25]……正弦阵列面的插补误差由 1.5 μm 降至 0.37 μm" | ✅（但见下） |

**回查暴露一个要留给第 22 周的细节**：第 4 条的数值是真数据，但它在原文里是
**转引他人工作**（"CHEN 等[25]提出……"）。对"回到页码"而言这是正确的；
若要做到"这是谁的工作"，答案里应保留"某某等提出"这种转述标记——
**引用可回查 ≠ 引用是第一手**，这是两个不同的验收项。

### 3.5 负样本：一次误操作送来的好数据

使用者误跑了一次 `--query "..."`（字面三个点）+ `--max-tokens 16384`：

- 模型输出 4 段全空 + 缺口声明"**资料中没有提供明确的用户问题**，无法依据候选片段确定答案主题"，
  引用 0/0/0 ——**0 编造，拒答行为正确**；
- 顺带暴露一个真问题：**无意义查询的候选全是"参考文献列表页"**（`References` / 书目段落，
  英文文献清单），它们是 dense 通道的天然高分项。这类页面对很多查询都"语义相近"，
  是潜在的污染源 → 登记为遗留（解析层给参考文献段落打标记并在检索时降权）。

### 3.6 成本

3 题共 6 次调用：prompt 18,622 + completion 9,495 token（含 4,096 的缓存命中，
说明固定指令前缀在部分调用上被复用了）。相比第 19 周的重排（20 次调用约 9.4 万输入），
量级很小。**但要记住成本结构**：每题两次调用里，第二次（组织）才是贵的那个，
而它之所以贵是因为"答案长"——所以"把答案写短"既能提高成功率也能省钱。

## 4. 踩坑

1. **预算按"答案要写多长 + 模型要想多久"给，不能按"我要的 JSON 有多长"给**（T32）。
   四段式 JSON 约 1.2k token，但思考可以到 4k——**4096 的预算从第一天就是错的**，
   只是在重排那种小 JSON 上侥幸没暴露。
2. **预算贴脸等于没给**：盘点预算 2048，实测有一题用了 2043（差 5 个 token 就白跑一次）。
   上限只在真生成时付费，所以宁可留余量。
3. **关键词判据要取"半步"**：`"有哪些方法"` 命不中 `"有哪些主流方法"`（见 2.5）。
4. **"最多 2 个引用"被理解成"可以写两个"**：R21-1 有一条把同一个 `文件:页` 连写两次
   → 校验层去重，计数按去重后算（这类小毛病不该动提示词）。
5. **架构上和规划写的不一样**（2.2）：不是随手改的，是"防成本失控"这个硬要求逼出来的；
   已写进笔记与台账，附件式的偏差也要留下痕迹。
