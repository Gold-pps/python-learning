## 3. Skill

### 结构

```text
.codex/skills/notes-qa-eval/
└── SKILL.md      frontmatter + 正文，最小 skill 只需这一个文件
```

frontmatter 格式：

```markdown
---
name: notes-qa-eval
description: 什么时候用这个 skill
---
```

### 关键发现

1. **Codex 会扫描项目级 `.codex/skills/`**，不限于用户级 `~/.codex/skills/`；
2. Skill 是**会话启动时加载**，新建后需要新会话才生效；
3. 触发靠 description 里的关键词（"跑一下评估""检查项目"）。

### 降级设计

第一版 skill 直接跑 `eval_cases.py`，在 Codex 沙箱里失败：
`APIConnectionError: Connection error.`——沙箱无网络，模型评估连不上 DeepSeek。

改法：

- `eval_cases.py` 加 `--unit-only` 参数（只跑 5+1 条单元测试，不走网络）；
- SKILL.md 明确指示：先跑 `--unit-only`，然后提示用户手动跑完整评估。

**通用经验**：给沙箱里的 Agent 写 skill，必须设计"无网络降级路径"。

## 4. MCP（filesystem）

### 配置

```bash
codex mcp add filesystem -- npx -y @modelcontextprotocol/server-filesystem .
```

然后手动把 `.` 改成绝对路径（`.codex/config.toml` 里存的是字面值，相对路径会随
启动目录漂移）。

最终 `~/.codex/config.toml`：

```toml
[mcp_servers.filesystem]
command = "npx"
args = ["-y", "@modelcontextprotocol/server-filesystem", "C:\\Users\\czy\\Desktop\\deepseek_project_1\\python-learning"]
```

### 踩坑：npx 首次下载被沙箱切断

第一次会话里 MCP 加载失败，Codex 报"本会话没有加载任何 MCP server"。
原因：npx 首次运行需要联网拉 `@modelcontextprotocol/server-filesystem`，沙箱不给网。

**解法**：在沙箱外先跑一次 `npx -y @modelcontextprotocol/server-filesystem --help`
预缓存。之后再开会话，MCP 正常加载。

### 验证

```text
• Called filesystem.list_allowed_directories({})
  └ Allowed directories:
    C:\Users\czy\Desktop\deepseek_project_1\python-learning
• Called filesystem.list_directory({...})
  └ [FILE] agent.py ...
```

**MCP 工具调用成功，边界锁定到仓库根。**

## 5. Subagents（部分可用）

### 第一次尝试：沙箱内跑

```bash
codex "派 3 个子代理并行审查 notes-qa 项目..."
```

Codex 确实 spawn 了 3 个子代理：


5 分钟无进展，中断。

### 第二次尝试：临时副本 + danger-full-access

为绕过沙箱限制，把仓库复制到 `%TEMP%\codex-subagent-test`，用 `--sandbox danger-full-access` 跑。

结果：
- 3 个子代理全部 **Completed**（比第一次更远）；
- 但主代理一直停在 `Waiting for agents`。

Codex 自己诊断出根因：

```text
• 子代理没有收到任务内容就结束了（fork 上下文未传递）。
```

### 精确结论

| 层面                 | 状态     |
| -------------------- | -------- |
| 子代理启动           | ✓ 成功   |
| 子代理执行（有网络） | ✓ 成功   |
| 任务载荷传递         | ✗ 空任务 |
| 结果回传主代理       | ✗ 死等   |

Codex 试了 4 种投递方式、5 轮，全部失败：
`spawn_agent` 的 message、`followup_task` 的 message、`send_message`、
"send_message 存简报 + followup_task 只写'查收件箱'"。

**这是 Codex v0.154.0 在 Windows + DeepSeek provider 下的一个具体缺陷**，
不是我们配置的问题。子代理能启动、能读 `AGENTS.md`、能跑测试，
只是收不到任务内容。

**未解决的边界**：`--sandbox danger-full-access` 会放开所有限制，
所以这次是在临时副本里跑的，不在主仓库。安全，但不方便日常用。

**待跟进**：等 Codex 修复载荷传递后重试；或换 Linux/macOS 环境试试。

## 6. 意外收获：Codex 审查发现并修复多个问题

Subagents 通道卡住时，主代理自己完成了审查（优雅降级），发现并修复了
以下问题。分两批：**第一批**是在沙箱内审查发现的；**第二批**是在临时副本
里跑 `danger-full-access` 时发现的。

### 第一批（沙箱内）

#### 6.1 read_note 非整数行号会抛异常（真 bug）

```text
read_note('学习进度.md', start_line='abc')
→ RAISED ValueError
```

设计文档要求"出错返回结构化错误，不抛异常"，这里是漏网的。

**修法**：`int()` 调用包在 try/except 里，捕获 `TypeError` 和 `ValueError`。

#### 6.2 must_cite 未归一化（评估假阴性）

模型写 `[第 7 周笔记.md:1-10]`（带空格），期望值 `第7周笔记.md`（无空格），匹配失败。

**修法**：`check_model_output` 里 `must_cite` 也用 `_normalize()` 比对。

#### 6.3 M3 期望词太弱（评估假阳性）

原期望词 `["没有"]`，导致 `"笔记里没有讲 Excel 画图，但讲了别的"` 也会 PASS。

**修法**：收紧为 `["没有找到"]`。实测模型本来就写"没有找到"，不影响通过率。

### 第二批（副本 + danger-full-access）

#### 6.4 search_notes 的 junction 逃逸漏洞（真漏洞）

**问题**：`search_notes` 用未 resolve 的 `NOTES_ROOT`，且不检查候选文件真实路径。
如果笔记根下有一个名为 `xxx.md` 的 junction 指向外部目录，
`search_notes` 会跟随进去，搜到根目录外的文件。

实测：

```text
在笔记根建一个名为 dir.md、指向外部目录的 junction
→ search_notes("PROBE-J2-MARKER-9f3")
→ {'file': 'dir.md\\secret.md', 'line': 1, 'snippet': 'PROBE-J2-MARKER-9f3'}
```

`list_notes` 已过滤，`search_notes` 没有——两者不一致。

**修法**：

- `search_notes` 的 `root` 改为 `config.NOTES_ROOT.resolve()`；
- 循环候选文件时用 `p.resolve().is_relative_to(root)` 复核，越界跳过；
- `list_notes` 同样加 resolve 复核，保持一致。

**加 U6 覆盖**：用一个以 `.md` 结尾的 junction 名字（不然 `rglob("*.md")`
不会扫到），实测三条路径（list / search / read）都拒绝。

#### 6.5 read_note 的 truncated 语义错误（真 bug）

原实现：`"truncated": actual_end < end_line`。

含义是"请求的结束行被截断了"，而不是"文件还有内容没读完"。
请求 `end_line=9999` 但文件只有 100 行时，`actual_end = 100 < 9999`，
返回 `truncated: True`——但其实是**读完了**。

**修法**：改成 `actual_end < total`——只有"没读到文件末尾"才算 truncated。

**加 U10 覆盖**：请求 9999 行、默认读到底两种场景。

#### 6.6 search_notes 的 max_results 类型检查（加固）

原实现：`int(max_results)` 直接调，传 `None` 或 `'many'` 会抛异常。

**修法**：包在 try/except 里，返回结构化错误。

**加 U8 覆盖**：覆盖 4 种畸形参数场景（read_note(None)、
search_notes max_results 非整数等）。

#### 6.7 超时与重试配置（加固）

**问题**：OpenAI Agents SDK 默认 HTTP 超时是 600 秒（10 分钟）。
网络卡住时命令行会长时间无输出。

**修法**：

- `config.py` 加三个常量：
  - `REQUEST_TIMEOUT = 60.0`（单次请求超时，秒）；
  - `MAX_RETRIES = 1`（SDK 重试次数）；
  - `OVERALL_TIMEOUT = 120.0`（一轮提问的总上限，覆盖"模型思考 + 工具调用 + 再次请求"的完整循环）。
- `AsyncOpenAI` 传 `timeout=REQUEST_TIMEOUT, max_retries=MAX_RETRIES`；
- `main.py` 用 `asyncio.timeout(config.OVERALL_TIMEOUT)` 包住 `Runner.run`。

**加 U12 覆盖**：只验证常量存在（配置防回归），不验证超时行为。

## 9. 我的复盘

- **最有用的一件事**：AGENTS.md。它让每次新会话不用重新解释项目背景，
  而且写一次长期有效；
- **最意外的发现**：Skill 不只放用户级目录，放项目级 `.codex/skills/` 也会被扫到，
  可以随 Git 一起走，换电脑也带着；
- **最大的教训**：沙箱无网络会影响三件事——模型评估、MCP 首次下载、Subagents。
  写任何"给 Codex 用的东西"都要先想：它需要网络吗？需要就设计降级；
- **最有价值的副产品**：让 Codex 审查自己的项目发现了 3 个真 bug，
  比人肉 review 有效率。以后可以每周做一次"Agent 审查"；
